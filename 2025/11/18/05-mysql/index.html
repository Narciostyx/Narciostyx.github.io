1. 概述

Boost.MySQL（命名空间 boost::mysql）是 Boost 官方提供的 MySQL 客户端库，让你用现代 C++ 直接访问 MySQL / MariaDB 服务器，而不需要依赖 libmysqlclient。

  • 定位：一个基于 Boost.Asio 的、header-only 的 MySQL 客户端协议实现。它自己实现了 MySQL 的客户端-服务器协议（握手、认证、文本查询、预处理语句、结果集、连接池），只需要 OpenSSL 作为外部依赖。
  • 编程模型：所有网络操作都提供 同步（抛异常 / error_code）与 异步（回调 / yield_context / C++20 协程）两套版本，异步版本可无缝接入任何 Asio 执行器（io_context、thread_pool 等）。
  • 类型安全：提供「动态接口」（results / field，运行时类型）和「静态接口」（static_results + C++ 结构体，编译期类型检查）两种取值方式。

典型使用场景：

  1. 需要嵌入 MySQL 访问能力、又不想引入 C 客户端库依赖的服务端程序（HTTP 服务、聊天服务、游戏后端）。
  2. 已经使用 Boost.Asio 的异步程序，希望数据库访问与网络 I/O 共用同一个事件循环，避免线程池 + 阻塞式客户端。
  3. 需要大量并发连接（连接池 + 协程）的高吞吐场景。
  4. 需要预处理语句、二进制协议以高效读写大量数值数据。
  5. 需要精细控制 TLS（自签 CA、证书校验、双向认证）的企业内网环境。

与替代方案的对比：相比 libmysqlclient（C API，阻塞、需手动管理连接与结果集），Boost.MySQL 是 header-only 的 C++ 库，天然支持异步与协程；相比 mysql-connector-c++，它更轻量、与 Asio 集成更自然，但不支持 MySQL 的全部高级特性（如 MFA、多因素认证、LOAD DATA LOCAL INFILE 等）。

版本与 API 演进（很重要，写代码前先确认自己的 Boost 版本）：

版本 新增能力
1.82 ~ 1.84 初版 API：connection<Stream> / tcp_ssl_connection、handshake_params、results、statement、throw_on_error
1.85 新 API：any_connection、connect_params、connection_pool、客户端 SQL 格式化 format_sql
1.86 pipeline（实验性）、is_fatal_error
1.87+ with_params、with_diagnostics 完成令牌、默认令牌改为 with_diagnostics(deferred)

本文以 1.85+ 的新 API（any_connection）为主，同时给出旧 API（connection<Stream>）的等价用法。

3. 核心概念

3.1 执行上下文 io_context 驱动一切

和所有 Asio 程序一样，先创建 asio::io_context（执行上下文），它承载事件循环、定时器与 socket 状态。所有 I/O 对象（连接、连接池）都绑定到它上面；只有调用 run() / poll()，异步操作才会真正推进。大多数程序只需要一个 io_context，即使同时管理成百上千个 MySQL 连接。

3.2 连接（connection）与握手

any_connection 表示一个到 MySQL 服务器的会话（session state + 内部 stream）。建立连接分两层：

  • connect(params) / async_connect(params)：高层 API。它负责域名解析、TCP/UNIX socket 连接、TLS 握手、MySQL 协议握手、认证，一次搞定。
  • handshake(params) / async_handshake(params)：低层 API。只做 MySQL 协议层的握手与认证，要求底层 stream 已经连接好（例如你自己用 asio::ip::tcp::socket 连好，或使用 connection<Stream> 自定义 stream）。

握手阶段双方还会协商：字符集/排序规则（connect_params::connection_collation，默认 utf8mb4_general_ci）、是否启用多语句（connect_params::multi_queries）、是否使用 TLS（connect_params::ssl）。

3.3 查询与预处理语句；文本协议 vs 二进制协议

库提供两条执行 SQL 的路径：

  • 文本查询（text protocol）：execute("SELECT ...", result)。SQL 以字符串形式发送给服务器，结果集里的所有值都按字符串返回，再由客户端解析成整数/浮点/日期等类型。简单、灵活，但解析开销大。
  • 预处理语句（prepared statement / binary protocol）：prepare_statement(sql) 得到 statement 句柄，再用 execute(stmt.bind(args...), result) 执行。SQL 模板只在服务器端解析一次，参数以二进制格式传输，结果也以二进制返回。适合：① 反复执行同一语句；② 传输大量数值数据；③ 需要彻底避免 SQL 注入。

第三种方式是客户端 SQL 格式化（with_params / format_sql，Boost 1.85+/1.87+）：客户端把 {} 占位符安全地展开成完整 SQL 字符串，然后走文本协议。它比预处理语句更简单，但每次都会产生不同的 SQL 文本（服务器无法复用执行计划）。

3.5 异步模型与协程

每个网络操作都有 async_* 版本，接受 Asio 完成令牌（completion token）。any_connection 与 connection_pool 的默认令牌是 with_diagnostics(asio::deferred)，因此可以直接 co_await，并且失败时抛出带诊断信息的 error_with_diagnostics。

同一时刻每个连接只能有一个未完成的异步操作：并发发起第二个会以 client_errc::operation_in_progress 失败。连接对象非线程安全（不同对象可跨线程，共享同一对象不行）；需要跨线程共享时请使用连接池 + pool_params::thread_safe，或在 strand 上运行。

3.6 SSL/TLS

TCP 连接默认使用 TLS（ssl_mode::enable：服务器支持就用，不支持则回退明文）。TLS 握手由 async_connect 内部完成，TLS 关闭由 async_close 完成。默认的 SSL 上下文不做证书校验，要校验必须自己传 asio::ssl::context：

UNIX socket 被视为安全通道，永远不使用 TLS（connect_params::ssl 被忽略）。连接建立后可用 uses_ssl() 查询是否加密。

3.7 错误处理（error_code + diagnostics）

库基于 boost::system::error_code。每个网络操作提供四种重载：① 同步抛异常（抛 error_with_diagnostics）；② 同步输出 error_code& + diagnostics&；③ 异步回调；④ 异步回调 + diagnostics&。

错误分为四类：客户端错误（client_errc）、MySQL/MariaDB 共有服务器错误（common_server_errc）、MySQL 专有（<boost/mysql/mysql_server_errc.hpp> 中的整数码）、MariaDB 专有（<boost/mysql/mariadb_server_errc.hpp>）。另外用 is_fatal_error(ec) 区分致命错误（连接状态未知，必须重连）与非致命错误（如 er_no_such_table，连接仍可继续使用）。

安全提示：diagnostics::server_message() 可能包含用户输入（例如导致出错的字段值），且使用连接的字符集编码，必须当作不可信输入处理。

3.8 连接池

connection_pool（Boost 1.85+，仅支持 any_connection）复用长连接：省去反复建立会话的开销，并内建重连、健康检查、超时与状态重置。使用三步：

  1. 构造 pool_params（地址、账号、库、池大小、TLS 等）并创建 connection_pool；
  2. 调用一次 async_run(asio::detached) 启动池任务；
  3. 用 async_get_connection() 取到 pooled_connection（独占所有权，operator-> 返回底层 any_connection），对象析构时连接自动归还池。

handshake / async_handshake void handshake(const handshake_params&) 只做 MySQL 层握手
execute / async_execute void execute(ExecutionRequest, results&) 文本查询或语句执行
prepare_statement / async_prepare_statement statement prepare_statement(string_view) 准备语句
start_execution / read_resultset_head / read_some_rows（含 async_*） 见 any_connection 多函数操作
set_meta_mode / meta_mode 元数据模式
stream Stream& stream() 访问底层 stream（旧 API 特有的逃生舱）
get_executor / uses_ssl 执行器 / 是否加密
quit / async_quit void quit() 发送 QUIT 并关闭 SSL（不关闭底层传输）
close / async_close void close() quit() + 关闭底层 socket
reset_connection / ping / close_statement 与 any_connection 同名同义
  • 要点：
    1. 旧 API 不解析域名，需要自己用 asio::ip::tcp::resolver 解析后把 endpoint 传给 connect。
    2. connect() 会先做握手再建立 TCP？——不会：必须先连好传输，connect 负责的是「连接端点 + 握手」的组合；直接使用 handshake() 时底层 stream 必须已连接（例如 UNIX socket）。
    3. quit() 与 close() 的区别：前者只结束会话（发 QUIT、关 TLS），后者还关闭 socket。
    4. 新代码请优先使用 any_connection（官方明确建议）。

5. 使用流程

5.1 同步：连接 → 查询 → 关闭

  1. 创建 asio::io_context ctx（所有 I/O 对象的宿主）。
  2. 构造 mysql::any_connection conn(ctx)（若要校验证书，构造时传入 mysql::any_connection_params{&ssl_ctx}）。
  3. 填充 mysql::connect_params params：server_address（host+port 或 unix path）、username、password、database、可选 ssl。
  4. conn.connect(params); —— 解析、TCP、TLS、握手、认证一步完成；失败抛 error_with_diagnostics。
  5. 准备一个 mysql::results result;，调用 conn.execute(sql, result);（或 conn.execute(stmt.bind(args...), result);）。
  6. 从 result.rows() / result.meta() / result.affected_rows() 读取数据；需要保留的数据用 as_vector() 或 row{view} 拷贝。
  7. 结束前 conn.close();（发 QUIT + TLS shutdown + 关闭 socket）。若 close() 抛异常，可以忽略并直接析构（析构会关闭底层传输，不会泄漏资源）。
  8. 同步模式下 io_context::run() 不是必须的（同步函数内部会驱动必要的 I/O）。

5.2 异步（C++20 协程）：连接 → 查询 → 关闭

  1. 写一个 asio::awaitable<void> 协程，参数里传入 mysql::any_connection&。
  2. 用 co_await conn.async_connect(params); 建立连接（出错抛 error_with_diagnostics）。
  3. 用 co_await conn.async_execute(sql, result); 执行查询。
  4. 在 main 中用 asio::co_spawn(ctx, coro(), [](std::exception_ptr e){ if (e) std::rethrow_exception(e); }); 启动协程。
  5. 调用 ctx.run(); 驱动事件循环——忘记它协程永远不会推进。
  6. co_await conn.async_close(); 干净关闭；随后 ctx.run() 返回。

变体：C++11 可用回调（conn.async_execute(sql, result, [](error_code, results&){...})）或栈式协程（asio::spawn + yield_context）。

5.3 预处理语句：prepare → execute → 读结果

  1. mysql::statement stmt = conn.prepare_statement("SELECT a, b FROM t WHERE id = ?");（异步：co_await conn.async_prepare_statement(sql)）。
  2. 检查 stmt.valid() 与 stmt.num_params()（应等于 SQL 中 ? 的个数）。
  3. mysql::results result; conn.execute(stmt.bind(id), result);（异步：co_await conn.async_execute(stmt.bind(id), result)）。
  4. 遍历 result.rows()，用 row_view::at(i) / field_view::as_*() 取值。
  5. 需要时重复第 3 步（同一语句可复用，参数可不同）。
  6. 用 conn.close_statement(stmt);（异步 co_await conn.async_close_statement(stmt)）释放服务器端资源；连接关闭时也会自动释放。

5.4 连接池：run → get_connection → 使用 → 归还

  1. 构造 mysql::pool_params params（地址、账号、库、initial_size、max_size、TLS、字符集策略、线程安全等）。
  2. mysql::connection_pool pool(ctx, std::move(params));。
  3. pool.async_run(asio::detached); —— 每个池只能调用一次，它负责建连与保活。
  4. 处理中：mysql::pooled_connection conn = co_await pool.async_get_connection(asio::cancel_after(std::chrono::seconds(5)));。
  5. 用 conn->async_execute(...) 正常使用（operator-> 得到 any_connection&）。
  6. 归还：让 conn 析构（会自动 reset），或 conn.return_without_reset(); 明确跳过 reset（确定没有修改会话状态时）。
  7. 关闭：pool.cancel();（通常在 signal_set 的回调里），然后 ctx.run() 返回、池析构。

5.5 多函数操作（分批读大结果集）

  1. mysql::execution_state st; co_await conn.async_start_execution(sql, st);
  2. 循环：while (!st.complete()) { if (st.should_read_rows()) { mysql::rows_view batch = co_await conn.async_read_some_rows(st); /* 处理这一批 */ } else if (st.should_read_head()) { co_await conn.async_read_resultset_head(st); } }
  3. 每批行只在下一次网络操作前有效，需要保留请立即拷贝。
  4. 多结果集场景同样用该循环，st.meta() 给出当前结果集的列元数据。

7. 常见问题与陷阱

1. 问题：用 rows_view / row_view / field_view 保存了数据，稍后再读却拿到垃圾值。

  • 原因：视图（*_view）不拥有内存，它指向 results 或连接内部缓冲区。read_some_rows() 返回的 rows_view 只在下一次网络操作之前有效；results 被复用后其视图也全部失效。
  • 解决：需要跨越下一次操作/下一次执行时，立即做拥有型拷贝：mysql::row r{row_view}、mysql::field f{field_view}、mysql::rows{rows_view}，或 row.as_vector() 得到 std::vector<field>。

2. 问题：异步程序什么也不做，回调/协程永远不执行。

  • 原因：忘了 ctx.run()（或 ctx.poll()）驱动事件循环；或者在协程里忘了 co_await，把 async_execute(...) 的返回值（延迟操作对象）直接丢弃了。
  • 解决：确保 io_context::run() 被调用并在操作完成前保持运行；协程里必须 co_await；如果使用 asio::deferred，要显式用某个令牌去启动它。

3. 问题：异步操作返回后参数或 results 对象已失效（悬垂引用）。

  • 原因：async_execute(sql, result) 会异步写入 result；如果把 result 放在会被提前销毁的作用域里（例如局部变量在回调触发前析构），就是 UB。同理 stmt.bind(...) 里的参数若用引用包装（std::ref）而原对象提前销毁也会出问题。
  • 解决：保证传给异步函数的 results / statement / 绑定参数的生命周期覆盖整个操作（放在成员变量或与 co_await 同一作用域）；with_params 默认按值拷贝参数，相对安全，但用 std::ref 时要自己保证生命周期。

4. 问题：field::as_int64() 抛 bad_field_access，或 get_int64() 返回乱值。

  • 原因：as_*() 是checked 访问（类型不匹配抛异常），get_*() 是unchecked（类型不匹配是未定义行为）。另外值为 NULL 时 is_int64() 等全部返回 false，只有 is_null() 为真。
  • 解决：先用 is_null() 判空，再用 is_int64() / is_string() 等判断类型，然后调用对应的 as_*()；只有在能静态保证类型（例如配合静态接口）时才用 get_*()。

5. 问题：多次执行查询后，之前的数据不见了 / affected_rows() 数值看起来是上一次的。

  • 原因：results 对象是可复用的容器，每次 execute() 会清空并覆盖它之前的内容（这是为了复用内存）。它没有公开的 clear() 成员。
  • 解决：把需要长期保留的数据拷贝出来（as_vector() / row{view}），或者在每次执行前把上一次结果处理干净；不要把 results 当作历史缓存。

6. 问题：连接 MySQL 8.0 报认证错误（unknown_auth_plugin 或认证失败）。

  • 原因：MySQL 8.0+ 默认认证插件是 caching_sha2_password。Boost.MySQL 在 1.88 及更早版本要求该插件必须通过 TLS；1.89+ 才支持明文连接。库也只实现了 mysql_native_password 与 caching_sha2_password，不支持其他插件与 MFA。
  • 解决：① 使用 TLS（默认 ssl_mode::enable 即可，服务器支持就会走加密）；② 或把用户改为 ALTER USER 'u'@'%' IDENTIFIED WITH mysql_native_password BY 'pwd';；③ 或升级到 Boost 1.89+。注意：若服务器的 default_authentication_plugin 是库不支持的插件，即使该用户用的是别的插件也不受支持。

7. 问题：MySQL 8 上正常的代码在 MariaDB 上报错码无法识别。

  • 原因：错误码分类不同。MySQL 专有码在 <boost/mysql/mysql_server_errc.hpp>，MariaDB 专有码在 <boost/mysql/mariadb_server_errc.hpp>，两者对应的 category 也不同（get_mysql_server_category() / get_mariadb_server_category()）；两者共有的码在 common_server_errc。
  • 解决：不要硬编码服务器专有错误码的枚举值，改用 common_server_errc 或比较整数码/category；对 MariaDB 避免使用 MySQL 8 特有语法与功能。

8. 问题：调用 handshake() 报错或卡住，而 connect() 正常。

  • 原因：handshake() / async_handshake() 是低层 API，只执行 MySQL 协议层握手与认证，不会建立 TCP 连接、不会解析域名、也不会做 TLS 握手；而 connect() 把这些全部做完（解析 + 传输连接 + TLS + 握手）。
  • 解决：普通场景用 connect() / async_connect()；只有在自定义 stream（例如已连接的 UNIX socket、自定义 socket 类型，或旧 API 的 connection<Stream>）上才使用 handshake()。

9. 问题：在同一个连接上并发发起两个异步操作，第二个立即失败（client_errc::operation_in_progress）。

  • 原因：any_connection 同一时刻只允许一个未完成的异步操作；并且连接对象非线程安全（不同对象可跨线程，共享同一对象不行）。
  • 解决：在同一个协程/回调链里串行 co_await 各个操作；需要并发请使用多个连接（推荐 connection_pool，必要时配合 pool_params::thread_safe = true）。

10. 问题：查询 SELECT 1 AS my_field 后 meta()[0].column_name() 是空字符串。

  • 原因：默认 metadata_mode::minimal，为省内存不保留列名/库名/表名等字符串元数据。
  • 解决：连接建立后调用 conn.set_meta_mode(mysql::metadata_mode::full);（只影响字符串成员，其他元数据始终可用）。

11. 问题：execute("SELECT ...; SELECT ...") 报语法错误。

  • 原因：多语句（multi-queries）默认关闭（安全加固），单次 execute 只允许一条语句。
  • 解决：在 connect_params::multi_queries = true 后重连；注意多语句会放大 SQL 注入的破坏力，开启后必须使用 with_params / 预处理语句等安全手段拼接 SQL。

12. 问题：读取超长行时报 client_errc::max_buffer_size_exceeded。

  • 原因：连接内部缓冲区默认上限 64MB，且单行必须整体放进缓冲区（数据集总大小不受此限制）。
  • 解决：构造连接时调大 mysql::any_connection_params{}.max_buffer_size（例如 0x20000000 表示 512MB）；连接池则调整 pool_params::initial_buffer_size（以及连接自身默认上限）。

13. 问题：连接池 async_get_connection() 永远不返回 / 报 client_errc::pool_not_running。

  • 原因：池必须先用 async_run() 启动，且每个池只能调用一次；另外默认 async_get_connection() 会一直等到有连接可用（服务器不可达时会等很久），池被取消时返回 pool_cancelled。
  • 解决：确认已调用 pool.async_run(asio::detached)；给取连接加超时 asio::cancel_after(std::chrono::seconds(5))；程序退出前用 pool.cancel() 停止池；注意连接池只支持 any_connection。
