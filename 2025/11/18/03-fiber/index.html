1. 概述

Boost.Fiber 是一个**用户态协作式线程（user-space cooperative thread）**库。它提供 boost::fibers::fiber——一种可被显式调度、可挂起/恢复的执行上下文，语义上接近 std::thread（join()、detach()、同步原语），但切换发生在用户态，不需要陷入内核。

  • 库的定位：把「并发」从「并行」中解耦出来。用 fiber 写出看似顺序、实际并发的代码（尤其是大量 I/O 等待、状态机、异步回调），而不用承受线程切换与栈内存的开销。
  • 切换成本：一次 fiber 上下文切换通常只需几十到上百个 CPU 周期；线程切换需要数千周期（陷入内核、TLB/缓存影响）。
  • 栈开销：每个 fiber 自带独立栈，默认 fixedsize_stack（Boost.Context 的默认大小，通常 128 KB）；因此 fiber 数量受内存约束，而不是受内核线程数约束。

典型使用场景

  1. 高并发网络服务：每个连接一个 fiber，代码是阻塞式写法，底层用非阻塞 I/O + 事件循环（Boost.Asio）驱动。
  2. 把回调式异步 API 改写成同步写法：用 promise/future 或 Asio 的 yield 完成令牌（completion token），在 fiber 内「同步」等待。
  3. 复杂状态机 / 协议解析：用 fiber 的栈保存中间状态，避免手写状态机或回调地狱。
  4. CPU 密集任务的分片调度：大量小任务用 work_stealing 调度器在多核上并行，同时保持任务内部逻辑顺序化。
  5. 已有事件循环的集成：在 GUI / 游戏主循环里每轮调用 this_fiber::yield()，把 fiber 调度器嵌进现有主循环。

与替代方案的对比

方案 切换成本 栈 抢占 适用
std::thread 高（内核） 独立，内核分配 抢占式 真正并行、阻塞式系统调用
Boost.Fiber 低（用户态） 独立，用户分配 协作式（需显式让出） 大量并发、I/O 密集、回调改写
C++20 协程 最低 无栈（需挂起时保存状态） 协作式 新代码、编译器支持良好
std::async / 线程池 高 独立 抢占式 简单任务并行

一句话：Boost.Fiber 是「有独立栈、可移植、C++11 起可用、与 Boost.Asio 深度集成」的用户态线程；代价是必须协作式让出，且不是 header-only。

关键点：Boost.Fiber 不是 header-only 库。 它内部通过 boost::context 的 boost::context::fiber（汇编实现的栈切换）完成上下文切换，这部分是预编译库。因此必须：

  1. 已构建（或安装）libboost_fiber 与 libboost_context；
  2. 编译时包含 Boost 头文件目录，链接时加上这两个库。

2.2 为什么依赖 boost::context

boost::fibers::fiber 的栈切换、callcc/ontop 机制全部由 boost::context 提供：

  • boost::context::fiber：可恢复的执行上下文（resume() / resume_with()）；
  • boost::context::fixedsize_stack / protected_fixedsize_stack / segmented_stack：栈分配器；
  • Boost.Fiber 的 boost::fibers::context 内部持有 boost::context::fiber，resume() 时即完成一次 fiber 切换。

因此不能只链接 boost_fiber；boost_context 是硬依赖（boost_fiber 的符号里引用了 boost::context::detail::*）。

2.3 线程本地存储（TLS）与 fiber 本地存储（FLS）的区别

这是使用 Boost.Fiber 最容易踩的坑，务必分清：

线程本地存储 TLS fiber 本地存储 FLS
声明方式 thread_local T x; / boost::thread_specific_ptr<T> boost::fibers::fiber_specific_ptr<T> p(cleanup);
作用域 每个线程一份 每个fiber一份
头文件 <thread> / <boost/thread/tss.hpp> <boost/fiber/fss.hpp>
生命周期 线程结束时析构 fiber 结束时调用 cleanup（若构造时提供）
迁移行为 不迁移 fiber 被迁移到别的线程后，FLS 随之迁移
典型用途 每线程的日志缓冲、随机数引擎 每 fiber 的「当前请求上下文」「连接对象」

要点：

  • 一个线程上可能同时运行成千上万个 fiber。若用 thread_local 存「当前 fiber 的上下文」，所有 fiber 会共享同一份数据，逻辑必然错乱。
  • 在 fiber 内应使用 fiber_specific_ptr<T>；它的初始值恒为 nullptr（不像 thread_local 会做默认构造）。
  • fiber_specific_ptr 对象本身必须活得比使用它的所有 fiber 更久（通常是全局/静态或调用方栈上的对象）。
  • 若某段数据确实属于「线程」（如 CPU 亲和性、每线程的 I/O 队列），继续用 thread_local 是对的。

2.4 配置宏（BOOST_FIBERS_*）

这些宏在编译 Boost.Fiber 库本身时定义（部分也可在用户代码中定义以影响头文件行为）：

宏 作用

3. 核心概念

3.1 协作式调度（cooperative scheduling）

fiber 不会被抢占。只有发生以下事件时才会切换：

  • 调用 boost::this_fiber::yield()；
  • 调用会阻塞的 fiber 感知 API（mutex::lock、condition_variable::wait、channel::pop、future::wait、this_fiber::sleep_for 等）；
  • fiber 函数返回（fiber 结束）。

3.2 每个线程一个调度器（scheduler）

  • 每个线程有独立的 boost::fibers::scheduler，默认算法是 algo::round_robin。
  • 调度器按线程懒创建：只有在该线程上创建 fiber 或调用 fiber 相关 API 时才实例化。
  • use_scheduling_algorithm<SchedAlgo>(args...) 只影响调用它的那个线程；要让多线程都参与共享调度，每个线程都必须各自调用一次。
  • 每个线程上还有一个隐式的 main fiber（main() 或线程函数所在的那个 fiber）和一个 dispatcher fiber（调度器内部使用，不会被迁移）。

3.3 fiber 的生命周期与栈

  • fiber 是 move-only：拷贝构造/赋值被删除。
  • 析构时若 joinable() 为真 → 调用 std::terminate()（与 std::thread 一致）。必须 join() 或 detach()。
  • 栈大小由栈分配器决定，可在构造时指定：
    • fixedsize_stack（默认，malloc/free，最轻量）
    • protected_fixedsize_stack（末尾有保护页，越界立即段错误；分配开销大）
    • pooled_fixedsize_stack（boost::pool 池化；非线程安全，每线程一个实例）
    • segmented_stack（按需增长；需 BOOST_USE_SEGMENTED_STACKS）

3.4 launch 策略：post 与 dispatch

  • post：正常并发语义，适合绝大多数场景。
  • dispatch：用于「立刻切换过去做点事再回来」的模式，也常用于让新 fiber 在当前线程上启动（便于设置 FLS 或与调度器交互）。

3.5 FLS 与 TLS

见 §2.3。一句话：fiber 内的「当前上下文」必须用 fiber_specific_ptr，不能用 thread_local。

3.6 fiber 迁移（migration）

  • 使用 work_stealing / shared_work 调度器时，一个就绪但未运行的 fiber 可能被另一个线程窃取并在那里运行。
  • 迁移是安全的：fiber_specific_ptr 会跟着走；this_fiber::get_id() 不变。
  • 正在运行的 fiber 不会被迁移；main fiber 与 dispatcher fiber 被「钉住」（pinned），永不迁移。
  • 迁移需要跨线程的原子操作，因此 BOOST_FIBERS_NO_ATOMICS 下不可用。

5. 使用流程

5.1 启动第一个 fiber 的最小流程

  1. #include <boost/fiber/all.hpp>。
  2. 编译时链接 -lboost_fiber -lboost_context（见 §2.5）。
  3. 在 main() 中构造 boost::fibers::fiber，传入可调用对象与参数。
  4. 用 join() 等待其结束；或 detach() 让它独立运行。
  5. 确保 fiber 对象在 join()/detach() 前一直存活（否则析构触发 std::terminate）。
  6. 整个 main 包在 try/catch 中（fiber 内异常会终止进程，且部分错误以异常形式从 join() 抛出）。

5.2 fiber 间同步的流程

选择顺序建议：先问「要不要传数据」→ 再问「要不要互斥」。

  1. 只传数据，不需要共享状态 → 用 buffered_channel<T>（有界队列）或 unbuffered_channel<T>（严格交接）。
    • 生产者循环 push()，结束时 close()；
    • 消费者循环 pop()，遇到 channel_op_status::closed 退出（或用 range-for）。
  2. 需要共享数据结构 → 用 fibers::mutex 保护，用 std::lock_guard/std::unique_lock 管理。
  3. 需要等待某个条件成立 → 用 condition_variable（配 fibers::mutex）或 condition_variable_any（配任意锁），并使用谓词重载。
  4. 需要等待「结果」而不是「信号」 → 用 promise/future（或 async()）；异常通过 promise::set_exception() 传回。
  5. 需要 n 个 fiber 同时起跑 → 用 barrier(n)。
  6. 不要用 std::mutex + std::condition_variable 在 fiber 内长等待：那会阻塞整个线程。

5.4 自定义调度器的流程

  1. 选择基类：
    • 不需要 per-fiber 属性 → 继承 boost::fibers::algo::algorithm；
    • 需要（如优先级）→ 继承 boost::fibers::algo::algorithm_with_properties<MyProps>。
  2. （属性版本）定义 MyProps : public boost::fibers::fiber_properties，构造函数接受 context* 并转发；任何影响调度的属性修改都要调用受保护的 notify()。
  3. 实现/重写五个方法：awakened、pick_next、has_ready_fibers、suspend_until、notify（属性版本用 awakened(context*, PROPS&)）。
    • 就绪队列建议直接用 boost::fibers::scheduler::ready_queue_type。
    • suspend_until(time_point::max()) 表示「无限期挂起」；否则用 std::condition_variable::wait_until 等到该时间点。
  4. （属性版本，可选）重写 property_change() 以在属性变化时重排队列；注意 ctx 可能不在队列里（正在运行或阻塞），需用 ctx->ready_is_linked() 判断。
  5. 在每个要使用它的线程上调用 use_scheduling_algorithm<MyScheduler>()，且要在其他 fiber 调用之前。
  6. 创建 fiber 时用 f.properties<MyProps>() 读写属性。

7. 常见问题与陷阱

7.1 fiber 不是线程：不能用 thread_local 存「当前 fiber 的数据」

  • 问题：在 fiber 内用 thread_local 变量保存每个逻辑任务的上下文，结果多个 fiber 互相覆盖数据。
  • 原因：thread_local 的作用域是线程。一个线程上会并发运行成千上万个 fiber，它们共享同一份 thread_local。
  • 解决：改用 boost::fibers::fiber_specific_ptr<T>（<boost/fiber/fss.hpp>），并为它提供清理函数；该对象必须活得比所有使用它的 fiber 更久（通常为全局/静态）。另外注意 fiber_specific_ptr 初始值是 nullptr，不像 thread_local 会默认构造。

7.2 fiber 函数抛出的异常会导致 std::terminate()

  • 问题：fiber 函数体里抛出未捕获异常，程序直接崩溃，且 join() 处什么都收不到。
  • 原因：fiber 有自己的栈与执行上下文，异常无法跨上下文传播；库在 fiber 顶层调用 std::terminate()。join() 只报告「结束了」，不报告「怎么结束的」。
  • 解决：
    1. 在 fiber 函数内总是包 try/catch(...)；
    2. 需要把异常传回调用方时，用 promise::set_exception(std::current_exception()) + future::get()（future::get() 会重新抛出）；
    3. 在 main 与线程函数最外层也加 try/catch，避免其他 Boost.Fiber API 抛出的异常直接终止进程。

7.3 fiber 数量可以很多，但受栈内存限制

  • 问题：想创建几十万 fiber，结果内存耗尽 / 分配极慢 / 栈溢出。
  • 原因：每个 fiber 有独立栈，默认 fixedsize_stack 使用 Boost.Context 的默认大小（通常 128 KB）。10 万个 fiber ≈ 12 GB 虚拟内存。
  • 解决：
    • 显式指定更小的栈：boost::fibers::fiber(std::allocator_arg, boost::context::fixedsize_stack(64 * 1024), fn)；
    • 开发/测试期用 boost::fibers::protected_fixedsize_stack（带保护页，栈越界立刻段错误，便于定位；但分配开销大）；
    • 频繁创建/销毁同类 fiber 时用 boost::fibers::pooled_fixedsize_stack（基于 boost::pool，非线程安全，每个线程一份实例）；
    • 需要栈按需增长时用 boost::fibers::segmented_stack（需定义 BOOST_USE_SEGMENTED_STACKS 且以 context-impl=ucontext 构建 Boost.Context，仅 gcc ≥ 4.7 / clang ≥ 3.4）。
    • 另外：减少 fiber 数量本身（用线程池 + 任务队列）往往比压栈更有效。

7.4 join() 之前必须保持 fiber 对象存活

  • 问题：在循环或作用域里临时构造 fiber 后立刻被析构，程序在析构点 std::terminate()。
  • 原因：fiber::~fiber() 在 joinable() 为真时调用 std::terminate()（与 std::thread 一致）。
  • 解决：
    1. 把 fiber 对象保存到容器/成员变量中，或延长其生命周期到 join() 之后；
    2. 不关心结果时显式 detach()；
    3. 记住 join() 之后对象变为 not-a-fiber，可以安全析构；
    4. fiber 是 move-only，存入 std::vector 请用 emplace_back / push_back(std::move(f))。

7.5 调度器必须在使用前设置，且每个线程各自设置

  • 问题：调用 use_scheduling_algorithm<algo::work_stealing>(n) 后，其他线程上的 fiber 仍然只在本线程跑；或某些线程根本没参与共享调度。
  • 原因：调度器是每线程一个，use_scheduling_algorithm 只影响当前线程；而 work_stealing 的 thread_count 参数必须所有参与线程传相同值。
  • 解决：
    1. 在每个要参与的线程开头调用一次 use_scheduling_algorithm<...>()，并且要在该线程上创建/操作 fiber 之前调用；
    2. 所有线程传一致的 thread_count（通常等于参与线程总数）；
    3. 主线程也要调用（否则主线程上的 fiber 不进入共享池）；
    4. 若希望空闲线程真正挂起而不是忙等，用 work_stealing(thread_count, /*suspend=*/true)。

7.6 阻塞的系统调用会卡住整个线程上的所有 fiber

  • 问题：某个 fiber 调用了 read()/fread()/std::this_thread::sleep_for()/同步 HTTP 请求等阻塞调用，同一线程上其他 fiber 全部停止响应。
  • 原因：Boost.Fiber 是协作式的，只有 fiber 感知的 API 才会让出。阻塞的系统调用会阻塞整个 OS 线程，调度器自然无法运行。
  • 解决：
    1. 把阻塞 I/O 换成非阻塞 I/O + 事件循环（Boost.Asio + round_robin 调度器 + yield）；
    2. 或临时方案：用 this_fiber::yield() 轮询（见 §5.3 方式 C）；
    3. 或把阻塞操作隔离到专用的 std::thread 中，通过 buffered_channel / future 与 fiber 通信；
    4. 长计算循环必须周期性调用 this_fiber::yield()。

7.7 用 std::mutex / std::condition_variable 做 fiber 同步

  • 问题：在 fiber 里用 std::mutex 等待，性能差甚至整体卡死。
  • 原因：std::mutex::lock() 竞争时会阻塞整个线程，该线程上的其他 fiber 也无法运行（对比 fibers::mutex 只挂起当前 fiber）。std::condition_variable 同理。
  • 解决：fiber 间同步用 boost::fibers::mutex / condition_variable（配 fibers::mutex）/ condition_variable_any（配 std::mutex）/ buffered_channel。只有跨线程共享数据时才用 std::mutex，且要避免在 fiber 内长时间持锁等待。

7.8 buffered_channel 的 capacity 不是元素个数

  • 问题：构造 buffered_channel<int> chan(1) 抛 std::invalid_argument；或以为容量为 8 的通道能存 8 个元素。
  • 原因：capacity 必须是 2 的幂且 ≥ 2（否则抛 std::invalid_argument）；且内部最多存 capacity - 1 个元素，达到该数量即视为「满」。
  • 解决：按「能存多少元素」+1 来选容量，并向上取 2 的幂（例如想存 7 个就用 8）。判断关闭请检查 pop()/try_pop() 返回的 channel_op_status::closed（官方 API 没有 is_closed()）。

7.9 future 未就绪时 promise 被销毁 → broken_promise

  • 问题：future::get() 抛出 boost::fibers::future_error，错误码 broken_promise。
  • 原因：promise 析构时既没 set_value() 也没 set_exception()，共享状态被标记为「已放弃」。
  • 解决：确保每条代码路径（包括异常路径）都调用 set_value() 或 set_exception()；用 try/catch(...) 包住 fiber 主体并在 catch 里 p.set_exception(std::current_exception())。另外 get_future() 每个 promise 只能调用一次，重复调用会抛 future_error。
