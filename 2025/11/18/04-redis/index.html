1. 概述

Boost.Redis 是一个构建在 Boost.Asio 之上的高级 Redis / Valkey 客户端库，
它实现了 Redis 的 RESP3 协议。
库自 Boost 1.84 起随 Boost 正式发行，1.87 起 API 趋于稳定（本文以 1.87 / 1.88 的 API 为准）。

它解决的问题：

  • 在 Asio 的异步模型下提供类型安全的 Redis 客户端：把 RESP3 的简单类型与聚合类型直接映射到
    std::string、int64_t、std::optional、std::vector、std::map 等 C++ 类型，避免手工解析协议。
  • 把「一个命令」「一条流水线」「一个事务」统一成同一种抽象（request），因此**自动流水线（auto-pipelining）**成为默认行为，
    而不是需要用户显式构造的特殊对象。
  • 把连接管理（DNS 解析、建连、TLS 握手、RESP3 握手、健康检查、自动重连）封装进一个长期存活的 connection 对象。

典型使用场景：

  1. 高并发的后端服务把 Redis 当作缓存 / 计数器 / 限流器，需要极低延迟与高吞吐。
  2. 需要用 C++20 协程（co_await）写出结构清晰的异步代码，而不是回调地狱。
  3. 需要在一个连接上同时进行普通请求/响应与 Pub/Sub 订阅（RESP3 的多路复用能力）。
  4. 需要连接 Redis Sentinel 集群并在故障转移后自动重新解析主节点地址。
  5. 需要 TLS 连接到托管 Redis（如云厂商提供的 rediss:// 端点）。

与替代方案的对比：

方案 特点
Boost.Redis 原生 Asio 异步模型、RESP3、协程、错误码、取消、零临时对象解析
hiredis C 库，同步/简单异步，需要自己管理协议解析与连接
redis-plus-plus 同步 API 友好，但依赖第三方事件循环做异步，流水线/事务需要新建连接，不支持 RESP3 与协程

一句话总结：如果你已经在用 Boost.Asio，并且需要高性能 + 现代 C++ 异步风格，Boost.Redis 是最自然的选择。

3.2 connection：长期存活的连接对象

boost::redis::connection 是一个长期存活的对象，它内部完成：

  1. 解析 config::addr（DNS）；
  2. 建立 TCP 连接；
  3. 如果 config::use_ssl == true，执行 TLS 握手；
  4. 发送 HELLO 3 完成 RESP3 握手（并按需带上 AUTH 参数）；
  5. 按 config::health_check_interval 周期性地发送 PING 做健康检查；
  6. 启动读写循环，把 async_exec 提交的请求写出去、把响应读回来；
  7. 连接断开后自动重连（间隔为 config::reconnect_wait_interval，设为 0 可禁用重连）。

这些工作全部由 async_run() 一个操作负责：

async_run 每个 connection 只应调用一次；它会一直运行到连接被 cancel() 为止。

3.3 请求/响应模型与 async_exec

  • boost::redis::request 表示「一条流水线」：一个或多个 Redis 命令。
  • boost::redis::connection::async_exec(req, resp) 把请求排队发送，并把每条命令的响应写入 resp。
  • 多个 async_exec 可以并发调用（来自不同协程/回调），实现内部会自动排队与合并写（coalescing）。

request 内部使用 std::string 存储 RESP3 载荷（payload()），因此可以 reserve() / clear() 复用缓冲区，避免重复分配。

3.4 RESP3 协议与响应适配

Boost.Redis 只支持 RESP3（不再支持 RESP2），这意味着：

  • 需要 Redis 6+；
  • 建连时会发送 HELLO 3；
  • 聚合类型区分更细（Array / Map / Set / Push / Attribute 等），可以直接映射到 std::map、std::set 等。

响应有两条路径：

响应类型 使用场合
response<T1, T2, ...>（即 std::tuple<adapter::result<T1>, ...>） 命令数量在编译期已知
generic_response（即 adapter::result<std::vector<resp3::node>>） 命令数量动态、响应含嵌套聚合、或需要处理任意 RESP3 结构

RESP3 类型到 C++ 类型的映射：

RESP3 类型 可用的 C++ 类型 类别
Simple-string std::string Simple
Simple-error std::string Simple
Blob-string std::string、std::vector Simple
Blob-error std::string、std::vector Simple
Number long long、int、std::size_t、std::string Simple
Double double、std::string Simple
Null std::optional<T> Simple
Array std::vector、std::list、std::array、std::deque Aggregate
Map std::vector、std::map、std::unordered_map Aggregate
Set std::vector、std::set、std::unordered_set Aggregate
Push std::vector、std::map、std::unordered_map Aggregate

3.5 发布订阅（Push 消息）

Redis 的 Pub/Sub 消息、键空间通知、客户端缓存失效通知等都以 RESP3 的 push 类型异步到达。
它们不占用 response<...> 的槽位，而是通过独立的接收通道交付：

  • 先用 connection::set_receive_response(resp) 指定接收对象；
  • 再调用 connection::async_receive(...)（或在 1.88 中用非阻塞的 connection::receive(ec) 先取缓存）；
  • push 数据被解析进 generic_response，用 boost::redis::consume_one(resp) 逐条消费。

3.9 关于「压缩」

Boost.Redis 本身不实现 RESP3 报文压缩：协议层没有压缩扩展，库也不依赖 zlib / brotli / zstd。
减少网络开销的推荐做法是：

  • 流水线批量化：把多个命令合并进一个 request，一次 async_exec（减少 RTT 与系统调用）；
  • 使用 push_range 一次写入大批元素（如 RPUSH / HSET）；
  • 对大对象应用层自行压缩（例如把 gzip 后的字节串存进 Redis），再在客户端解压。

如果一定要在传输层压缩，可以自行扩展 basic_connection 的读写路径，但这超出了库的公开 API 范围。

3.10 日志

connection::async_run 是一个复杂算法（含重连），因此库内置了一个轻量 logger，默认把部分状态信息打到 stderr。
可以通过向构造函数传 boost::redis::logger 控制级别：

日志级别是 syslog 风格：disabled、emerg、alert、crit、err、warning、notice、info、debug。
级别为 N 时只输出严重性 ≥ N 的消息（例如 level::err 会隐藏所有 info 类输出）。
config::log_prefix 会给每条日志加前缀（默认 "(Boost.Redis) "）。

rebind_executor template<class Executor1> struct rebind_executor { using other = basic_connection<Executor1>; } 换绑执行器（仅 basic_connection）
  • 要点：
    1. async_run() 必须先于任何 async_exec() 生效；否则请求会一直排队等待连接建立。
    2. connection 通常用 std::shared_ptr 管理，并用 asio::consign(asio::detached, conn) 让 async_run 持有它，
      保证连接在异步操作完成前不被销毁。
    3. 1.88 起默认完成令牌是 asio::deferred，所以回调风格必须显式传 completion token（如 lambda、asio::detached）。
    4. cancel(operation::all) 会同时取消解析、重连、健康检查、读写与未写出的请求，是推荐的关闭方式。
    5. 构造函数里默认执行了 set_receive_response(ignore)，也就是说在调用 set_receive_response 之前，
      所有 push（订阅消息、键空间通知等）都会被丢弃      。要接收 push 必须先绑定自己的 generic_response。

5. 使用流程

5.1 连接 + 发送请求 + 处理响应

  1. 准备配置：创建 boost::redis::config cfg;，按需设置 cfg.addr.host / cfg.addr.port /
    cfg.username / cfg.password / cfg.use_ssl / cfg.health_check_interval / cfg.reconnect_wait_interval。
  2. 创建执行上下文：boost::asio::io_context ioc;（协程版本还需要 co_spawn）。
  3. 创建连接对象：auto conn = std::make_shared<boost::redis::connection>(ex);
    用 shared_ptr 保证生命周期覆盖所有异步操作。
  4. 启动连接：conn->async_run(cfg, {}, boost::asio::consign(boost::asio::detached, conn));
    —— 解析 → 建连 → TLS 握手 → HELLO 3 → 健康检查 → 读写循环。必须早于 async_exec。
  5. 构造请求：boost::redis::request req; req.push("SET", "k", "v"); req.push("GET", "k");
  6. 准备响应对象：boost::redis::response<std::string, std::optional<std::string>> resp;
    槽位个数必须等于会产生响应的命令数。
  7. 执行：co_await conn->async_exec(req, resp, boost::asio::use_awaitable);
    （或回调 conn.async_exec(req, resp, handler);）
  8. 检查结果：判断完成签名中的 error_code；成功则用 std::get<N>(resp).value() 取值，
    失败则查看 std::get<N>(resp).error().diagnostic 或 ec.message()。
  9. 复用：req.clear();（保留缓冲区）后可以重新组装下一条请求。

5.2 订阅（Pub/Sub）流程

  1. 创建 connection 并 async_run（同 5.1 的第 1–4 步）。
  2. 准备接收对象：boost::redis::generic_response push_resp;
  3. 绑定接收对象：conn->set_receive_response(push_resp);（必须在任何接收操作之前调用，且对象要一直存活）。
  4. 构造订阅请求：boost::redis::request sub; sub.push("SUBSCRIBE", "channel");
  5. 执行订阅：co_await conn->async_exec(sub, boost::redis::ignore, boost::asio::use_awaitable);
    —— 注意 SUBSCRIBE 不占响应槽位。
  6. 进入接收循环：while (conn->will_reconnect()) { ... }
    1. 先尝试非阻塞取缓存：conn->receive(ec);
      若 ec == boost::redis::error::sync_receive_push_failed，清空 ec 并改为
      co_await conn->async_receive(boost::asio::redirect_error(boost::asio::use_awaitable, ec));
    2. ec 非空说明连接断开：跳出内层循环，回到外层重新 SUBSCRIBE（重连后需要重新订阅）。
    3. 消费 push：从 push_resp.value() 中读取（pubsub 消息通常是
      [0]=="message", [1]==channel, [2]==payload），然后调用 boost::redis::consume_one(push_resp);
      丢弃这一条，继续处理下一条。
  7. 需要退出时：conn->cancel(operation::all);，让 async_receive 与 async_run 一起返回。

5.3 优雅关闭

  1. 停止接收新请求（业务层保证不再调用 async_exec）。
  2. 等待在途请求完成，或直接放弃：conn->cancel(operation::exec); 取消尚未写出的请求。
  3. 取消整个连接：conn->cancel(operation::all);
    —— 这会取消解析/建连/TLS 握手/健康检查/重连/读写/未写出的请求。
  4. async_run 的完成处理器被调用（通常带 asio::error::operation_aborted），此时连接不再重连。
  5. 停止事件循环：让所有 handler 跑完后 ioc.run() 自然返回；如果还有定时器等长期操作，
    显式调用 boost::asio::post(ioc, [&]{ ioc.stop(); }); 或 ioc.stop();。
  6. 释放资源：shared_ptr<connection> 的最后一个引用消失，连接析构。
    如果使用了 asio::consign(asio::detached, conn)，请确认 handler 已执行完毕再销毁 ioc。

7. 常见问题与陷阱

7.1 问题：async_exec 一直不返回，程序像卡住了

  • 原因：async_exec 只负责「排队 + 发送」，真正的解析/建连/握手/读写循环由 async_run 驱动。
    如果没有先调用 async_run，请求会一直排队等待连接建立。
  • 解决：确保每个 connection 都调用了 async_run(cfg, {}, ...)，并且它在 async_exec 之前就已经启动；
    同时确认 io_context::run() 真的在跑（且没有被 ioc.stop() 提前终止）。

7.2 问题：连接建立前调用 async_exec，是应该等待还是立即失败？

  • 原因：默认行为是排队等待，直到连接建立后自动发出。
  • 解决：
    • 想「快速失败」：设置 req.get_config().cancel_if_not_connected = true;，
      此时 async_exec 会以 boost::redis::error::not_connected 完成。
    • 想「断开后重发幂等命令」：设置 req.get_config().cancel_if_unresponded = false;
      （注意：INCR、LPUSH 这类非幂等命令不能这么用，可能被执行两次）。
    • 想「不因连接丢失而失败」：cancel_on_connection_lost = false（默认 true）。

7.3 问题：程序随机崩溃 / async_run 访问已释放的 connection

  • 原因：connection 被提前析构。常见的坑是把 connection 放在局部作用域（栈上）或者 shared_ptr 的引用计数
    在异步操作完成前归零，而 async_run、async_exec、async_receive 仍在运行。
  • 解决：用 std::shared_ptr<connection>，并用 asio::consign(asio::detached, conn) 让 async_run 持有它： 同理，传给 async_exec 的 request 与 response 对象也必须活到操作完成（协程版本因为 co_await 天然满足）。

7.4 问题：什么都没发生，回调一次都没被调用

  • 原因：忘记运行 io_context，或者 ioc.run() 在所有 handler 注册前就已经返回（例如在 run() 之后才提交请求）。
  • 解决：
    • 在 ioc.run() 之前完成所有异步操作的提交；
    • 协程版本使用 asio::co_spawn(ioc, co_main(cfg), asio::detached); ioc.run();
    • 若使用 asio::consign(asio::detached, conn) 且 ioc.run() 提前返回，可调用
      boost::asio::executor_work_guard 或检查是否所有操作都已被取消。

7.5 问题：订阅到了消息，但 response<...> 里读不到

  • 原因：Pub/Sub 消息是 RESP3 push，不是命令响应；SUBSCRIBE / PSUBSCRIBE / UNSUBSCRIBE
    本身也不产生普通响应，因此不占用 response<...> 的槽位。
  • 解决：
    1. 用 conn->set_receive_response(push_resp); 绑定 generic_response；
    2. 用 conn->async_receive(...)（或 receive(ec) 非阻塞探测）接收；
    3. 用 boost::redis::consume_one(push_resp); 逐条消费（一次可能收到多条）；
    4. 订阅请求用 co_await conn->async_exec(req, ignore, use_awaitable); 执行，不要写进 response 元组。

7.6 问题：async_exec 成功但 std::get<N>(resp).value() 抛异常

  • 原因：响应类型与 Redis 实际返回的 RESP3 类型不匹配（例如 SET 在某些情况下返回 null，
    或把 HGETALL 的 map 读进 std::string）。adapter::result<T> 里存的是一个 adapter::error，
    .value() 在失败时抛 system::system_error。
  • 解决：
    • 先用 if (!std::get<N>(resp)) 检查，再读取 std::get<N>(resp).error().diagnostic 定位；
    • 不确定类型的命令（如 SET）用 std::optional<std::string>；
    • 嵌套聚合 / 动态条数用 generic_response；
    • 响应槽位数量必须与命令数一致，否则会出现 incompatible_size。

7.7 问题：请求长时间挂起，无法设置超时

  • 原因：async_exec 会等待连接建立，服务器宕机时可能挂起很久。
  • 解决：
    • 推荐用 Asio 的完成令牌：co_await conn->async_exec(req, resp, asio::cancel_after(10s));
      （内部走 per-operation cancellation 机制）；
    • 手动方案：起一个 asio::steady_timer，到期时调用 conn->cancel(operation::exec); 注意 cancel(operation::exec) 只取消尚未写出的请求；已经写出等待响应的请求不会被取消，
      这种情况下应改用 cancel(operation::all) 或直接放弃该连接。
    • 所有异步操作完成时都会收到 asio::error::operation_aborted，据此区分「超时取消」与「真实错误」。

7.8 问题：连接失败，日志里反复出现重连信息

  • 原因：这是设计行为——async_run 会按 reconnect_wait_interval 无限重试，并默认把状态打到 stderr。
  • 解决：
    • 用日志定位问题（主机名、端口、认证），logger 可以过滤级别： 或完全关闭：logger{logger::level::disabled}；
    • 不想重连时设置 cfg.reconnect_wait_interval = std::chrono::seconds::zero();
      或调用 conn.cancel(operation::reconnection);。

7.9 问题：HELLO 失败，错误码是 boost::redis::error::resp3_hello

  • 原因：Redis 版本低于 6（不支持 RESP3/HELLO），或用户名/密码错误，或 ACL 不允许该用户执行 HELLO。
  • 解决：
    • 确认服务端版本：redis-cli INFO server | findstr redis_version（需 ≥ 6.0）；
    • 确认 config::username（默认 "default"）与 config::password 正确；
    • 在 redis-cli -3 里手动执行 HELLO 3 AUTH <user> <pass> 验证凭据；
    • Boost.Redis 不支持 RESP2，无法降级到旧协议。

7.10 问题：链接错误 multiple definition of ... / undefined reference to ...

  • 原因：<boost/redis/src.hpp> 被多个翻译单元包含（重复定义），或者一个都没包含又没有链接 boost_redis
    （未定义引用）。
  • 解决：二选一——(a) 链接 -lboost_redis；(b) 在恰好一个 .cpp 中 #include <boost/redis/src.hpp>。
    另外别忘了链接 OpenSSL（-lssl -lcrypto），否则会出现大量 SSL_* 未定义引用。
