1. 概述

Boost.Beast 是一个构建在 Boost.Asio 之上的 C++ 网络协议库，实现了 HTTP/1 与 WebSocket（RFC6455） 两种协议，并提供同步、异步、缓冲导向（buffer-oriented）三套 API。

它解决的问题：

  • 用值语义的 C++ 类型（http::request / http::response / http::message）替代手写文本解析；
  • 用 Boost.Asio 的异步模型统一处理网络 I/O，避免自己写事件循环；
  • 提供**分层流（layered stream）**机制，让 HTTP、WebSocket、SSL/TLS 可以像积木一样叠加；
  • 提供超时、缓冲区、错误码等生产级基础设施，而不必自己管理 steady_timer。

Beast 明确不提供（官方在 HTTP 一节开头就给出了警告）：Basic Authentication、mime/multipart 编码、Cookie、重定向自动跟随、gzip 传输编码、缓存、代理等高层功能。这些需要用户基于 Beast 的消息类型自行实现。

典型使用场景：

  1. 编写高性能 HTTP 客户端 / 爬虫 / API 调用工具；
  2. 编写嵌入式或轻量级 HTTP 服务端（不依赖完整 Web 框架）；
  3. 编写 WebSocket 客户端 / 服务端（聊天、推送、实时行情、游戏）；
  4. 编写需要 WSS（WebSocket over TLS）的客户端；
  5. 编写 HTTP 反向代理 / 中继（官方 http_relay 示例）；
  6. 需要精确控制缓冲区、超时、内存分配的高并发服务。

与替代方案的对比：

方案 定位
Boost.Beast 头文件为主、贴近 Asio、零额外运行时依赖、性能优先、API 偏底层
cpp-httplib 极简同步 HTTP，代码量小，但无 WebSocket 异步模型
libcurl 客户端功能齐全（含重定向/Cookie/认证），但服务端能力弱
Boost.Asio + 手写解析 完全可控但极易出错，Beast 就是它的“正确版本”

3. 核心概念

3.1 执行上下文、执行器与 strand

所有 I/O 都需要一个 net::io_context。异步操作的完成处理器由 executor（执行器） 投递执行。

要点：

  • ioc.run() 在没有“工作”时返回；只要还有未完成的异步操作，它就会阻塞。
  • 多线程时 ioc.run() 可被多个线程同时调用；此时必须给每个 I/O 对象绑定 strand，否则数据竞争。
  • 给 I/O 对象构造时传 net::make_strand(ioc)，之后所有异步操作自动在该 strand 上执行，无需 bind_executor。

3.2 流与分层流（Stream / Layered Stream）

Beast 的所有算法都以 Stream 概念为模板参数：

概念 含义
SyncReadStream / SyncWriteStream / SyncStream 阻塞式读写
AsyncReadStream / AsyncWriteStream / AsyncStream 异步读写

“分层流”是指一个流的下一层（next_layer）还是另一个流，形成编译期单向链表：

要点：

  • next_layer() 只返回紧邻的下一层；get_lowest_layer() 递归返回最底层（通常是 tcp_stream）。
  • 使用 SSL 的 WebSocket 必须额外 #include <boost/beast/websocket/ssl.hpp>，否则 teardown 定制点缺失导致编译错误。

3.3 动态缓冲区（DynamicBuffer）

flat_buffer / multi_buffer 是读操作的“工作区”，在异步场景下必须比操作活得久。

类型 内存 缓冲区段数 稳定性
flat_buffer 动态（可设置上限） 恒为 1 prepare/consume 会失效旧 buffer
multi_buffer 动态 任意多 现有 buffer 保持稳定
flat_static_buffer<N> 栈/类内静态 恒为 1 无堆分配
static_buffer<N> 栈/类内静态 1~2 环形缓冲，可能失效

3.4 消息、Header、Body、Fields

Beast 用 http::message 模板建模 HTTP 消息，其继承关系为：

  • Fields 决定头部字段容器（默认 http::fields）；
  • Body 决定 message::body() 的类型以及解析/序列化算法；
  • request<Body> = message<true, Body>，response<Body> = message<false, Body>。

3.5 解析与序列化：parser / serializer

层级 读 写 说明
6 read write 一次收发完整消息
5 read + parser write + serializer 可配置 body_limit、缓冲区大小
4 read_header write_header 只收发头部
3 read_some write_some 增量收发，返回实际字节数
2 parser::on_chunk_header / on_chunk_body make_chunk / make_chunk_last 手工控制 chunk
1 parser 成员 serializer 成员 直接操作缓冲区

3.6 超时模型

Beast 有两套互斥的超时机制：

  1. beast::tcp_stream（basic_stream）——用于 HTTP 和普通 TCP。用 expires_after() / expires_never() 设置逻辑操作超时（一次逻辑操作可能包含多次异步调用）。
  2. websocket::stream_base::timeout——WebSocket 专用，含 handshake_timeout / idle_timeout / keep_alive_pings。

超时触发时，未完成的异步操作会以 beast::error::timeout 完成，并且实现已经关闭了 socket，无需再手动关闭。

    1. buffer_body 用尽缓冲区时返回 http::error::need_buffer，这不是致命错误，应清除后继续。
    2. file_body 需先 res.body().open(path, beast::file_mode::scan, ec)，并用 res.content_length(size) 显式设置长度（因为 prepare_payload 不会为文件调用 size()）。
    3. 自定义 body 只需提供 value_type，以及可选的 reader / writer 嵌套类型。

5. 使用流程

5.1 HTTP 客户端（同步）

  1. 解析命令行参数，取得 host、port、target、HTTP 版本（10 / 11）。
  2. 创建 net::io_context ioc;。
  3. 创建 tcp::resolver resolver{ioc}; 和 beast::tcp_stream stream{ioc};。
  4. auto const results = resolver.resolve(host, port); 做 DNS 解析。
  5. （可选）stream.expires_after(std::chrono::seconds(30)); 设置超时。
  6. stream.connect(results); 建立 TCP 连接。
  7. 构造请求：http::request<http::empty_body> req{http::verb::get, target, version};，然后 req.set(http::field::host, host);、req.set(http::field::user_agent, BOOST_BEAST_VERSION_STRING);。
  8. http::write(stream, req); 发送请求。
  9. beast::flat_buffer buffer; http::response<http::dynamic_body> res; http::read(stream, buffer, res); 接收并解析响应。
  10. 使用 res（如 std::cout << res;）。
  11. 收尾：beast::error_code ec; stream.socket().shutdown(tcp::socket::shutdown_both, ec);，忽略 beast::errc::not_connected。
  12. 异常通过 try/catch (std::exception const&) 统一处理。

5.2 HTTP 服务端（异步）

  1. 解析 address、port、doc_root、threads。
  2. net::io_context ioc{threads};。
  3. 创建 listener（持有 tcp::acceptor）：open → set_option(reuse_address) → bind → listen，每步用 error_code 检查。
  4. listener::run() → do_accept()：acceptor_.async_accept(net::make_strand(ioc_), handler)，为每条连接分配独立 strand。
  5. 在 on_accept 中 std::make_shared<session>(std::move(socket), doc_root)->run();，然后再次 do_accept() 继续接受新连接。
  6. session::run() 用 net::dispatch(stream_.get_executor(), ...) 切到正确的 strand。
  7. do_read()：先 req_ = {}; 重置请求对象（否则行为未定义），stream_.expires_after(30s)，再 http::async_read(stream_, buffer_, req_, handler)。
  8. on_read 中若 ec == http::error::end_of_stream 则走 do_close()；否则调用路由函数 handle_request(*doc_root_, std::move(req_)) 得到 http::message_generator。
  9. send_response()：记录 msg.keep_alive()，然后 beast::async_write(stream_, std::move(msg), handler)。
  10. on_write 中若 keep_alive 为 false → do_close()；否则回到步骤 7 读取下一个请求。
  11. do_close()：stream_.socket().shutdown(tcp::socket::shutdown_send, ec); 发送 TCP 半关闭。
  12. 主线程 ioc.run()，其余线程在 std::vector<std::thread> 中同样调用 ioc.run()。

5.3 WebSocket 客户端（异步）

  1. net::io_context ioc;。
  2. 构造 session，其成员为 tcp::resolver resolver_{net::make_strand(ioc)} 与 websocket::stream<beast::tcp_stream> ws_{net::make_strand(ioc)}，以及 beast::flat_buffer buffer_。
  3. resolver_.async_resolve(host, port, ...)。
  4. on_resolve：beast::get_lowest_layer(ws_).expires_after(30s);，然后 async_connect(results, ...)。
  5. on_connect：beast::get_lowest_layer(ws_).expires_never();（关键，关闭 TCP 超时）；ws_.set_option(websocket::stream_base::timeout::suggested(beast::role_type::client));；设置 decorator；把 host_ += ':' + std::to_string(ep.port());。
  6. ws_.async_handshake(host_, "/", ...)。
  7. on_handshake：ws_.async_write(net::buffer(text_), ...)。
  8. on_write：ws_.async_read(buffer_, ...)。
  9. on_read：处理数据（buffer_.data()），然后 ws_.async_close(websocket::close_code::normal, ...)。
  10. on_close：确认优雅关闭；打印 beast::make_printable(buffer_.data())。
  11. ioc.run() 直到所有操作完成。

5.4 WebSocket 服务端（异步）

  1. net::io_context ioc{threads};。
  2. 创建 listener：open → reuse_address → bind → listen。
  3. do_accept()：acceptor_.async_accept(net::make_strand(ioc_), ...)。
  4. on_accept：std::make_shared<session>(std::move(socket))->run(); 再 do_accept()。
  5. session 构造：ws_(std::move(socket))，websocket::stream<beast::tcp_stream> 直接接管 socket。
  6. run()：net::dispatch(ws_.get_executor(), ...) 切到 strand。
  7. on_run()：ws_.set_option(stream_base::timeout::suggested(beast::role_type::server));；ws_.set_option(stream_base::decorator(...)) 设置响应头（如 Server）；然后 ws_.async_accept(...)。
  8. on_accept：do_read()。
  9. on_read：若 ec == websocket::error::closed 直接返回（对端正常关闭）；否则 ws_.text(ws_.got_text()); ws_.async_write(buffer_.data(), ...)。
  10. on_write：buffer_.consume(buffer_.size()); 清空缓冲区，然后 do_read() 继续下一轮。
  11. 若需要主动关闭：ws_.async_close(websocket::close_code::normal, ...)。
  12. 多线程下 ioc.run() 在所有线程中调用。

7. 常见问题与陷阱

7.1 异步操作期间缓冲区 / 消息对象被销毁

  • 问题：异步读一开始就正常返回，但回调里数据是垃圾或直接崩溃。
  • 原因：beast::flat_buffer、http::request/response、parser、serializer 都是异步操作的外部状态，Beast 只保存指针。若它们是被调函数的局部变量，函数返回后立即析构。
  • 解决：把它们作为 session 的成员，并让 session 由 std::shared_ptr + std::enable_shared_from_this 管理，回调里用 shared_from_this() 续命。例如 http_client_async.cpp 中 buffer_、req_、res_ 都是成员。

7.2 body() 改了但响应没有 body / Content-Length 不对

  • 问题：res.body() = "..." 之后客户端收到空 body 或直接挂住。
  • 原因：body() 只是设置 body 容器，不会同步 Content-Length / Transfer-Encoding 字段；HTTP/1.1 下没有长度信息的消息会被视为无 body 或需要读到 EOF。
  • 解决：设置完 body 后调用 res.prepare_payload()；它会按 body 类型与内容自动选择 Content-Length 或 Transfer-Encoding: chunked。若使用 file_body，官方示例选择在打开文件后缓存 body.size() 并显式 res.content_length(size)，这样更明确也更高效。

7.3 keep_alive 与连接复用

  • 问题：服务端在 HTTP/1.1 下每处理一个请求就关闭连接，性能差；或反过来，客户端已关闭却仍在复用。
  • 原因：是否复用由 Connection 字段决定，而 Beast 把它映射成 keep_alive()。服务端必须把请求的 keep-alive 意图回填到响应，否则语义不一致。
  • 解决：
    • 服务端：res.keep_alive(req.keep_alive());，并在发送后检查 msg.keep_alive() 决定是否继续循环。
    • 客户端：只有 res.keep_alive() == true 且消息被完整读取（http::read 已保证）时才能复用同一连接。

7.4 在 async_* 调用中传入临时对象

  • 问题：http::async_write(stream, make_request(), handler) 编译通过但运行崩溃。
  • 原因：异步发起函数不复制消息，只持有引用；临时对象在语句结束即销毁。
  • 解决：消息必须是有名字、生命周期足够长的对象（通常作为 session 成员）。同理，beast::async_write(stream, std::move(msg), handler) 的 msg 也必须先存成局部变量，std::move 只是把它交给操作持有，变量本身不能是临时量表达式。

7.5 WebSocket 关闭后回调里拿不到 error::closed

  • 问题：对端发了 close 帧，自己的读回调却报别的错误，或一直阻塞。
  • 原因：error::closed 只在有读操作在进行时才会被投递；Beast 会自动回复 close 帧并关闭底层连接，但需要一次读来驱动。
  • 解决：保持一个读操作常驻（服务端 echo 循环天然如此）；主动关闭用 close() / async_close()，它会发送 close 帧、读掉剩余数据、收到对端 close 后关闭连接。服务端回调里应把 ec == websocket::error::closed 当作正常结束处理而不是错误。

7.6 需要超时却用了裸 tcp::socket

  • 问题：对端断网后程序永久卡住；自己写 steady_timer 又容易漏 cancel。
  • 原因：net::ip::tcp::socket 不提供超时（可移植性要求，网络库不为同步操作提供超时）。
  • 解决：改用 beast::tcp_stream（basic_stream 的别名）。用 expires_after() 设置逻辑操作超时，超时后实现会关闭 socket 并以 beast::error::timeout 完成操作；expires_never() 关闭超时。

7.7 与 WebSocket 组合时忘记关闭 tcp_stream 的超时

  • 问题：WebSocket 连接在空闲一段时间后被莫名关闭，或行为不稳定。
  • 原因：WebSocket 有自己的一套超时（stream_base::timeout），官方明确说明二者不兼容，同时在 tcp_stream 上保留超时会导致未定义行为。
  • 解决：连接建立后立刻 beast::get_lowest_layer(ws).expires_never();，然后只使用 ws.set_option(websocket::stream_base::timeout::suggested(...))。

7.8 SSL：在错误的层做握手

  • 问题：ws.handshake(...) 报协议错误，或编译报 teardown 相关错误。
  • 原因：SSL 握手属于下一层的操作，必须在 ws.next_layer() 上调用；此外 WebSocket 的关闭流程需要 teardown 定制点，<boost/beast/websocket/ssl.hpp> 未包含时不会提供。
  • 解决：
    1. #include <boost/beast/websocket/ssl.hpp>；
    2. 顺序固定：TCP 连接 → ws.next_layer().handshake(ssl::stream_base::client) → ws.handshake(host, target)；
    3. 设置 SNI 与主机名校验（SSL_set_tlsext_host_name / ssl::host_name_verification）。

7.9 缓冲区太小导致性能差或分配抖动

  • 问题：WebSocket 吞吐低，或频繁 realloc。
  • 原因：flat_buffer 默认从很小的容量开始按几何增长；WebSocket 读缓冲也有建议大小。
  • 解决：
    • 预估典型消息大小后给缓冲区设上限：beast::flat_buffer buffer{64 * 1024};（构造参数是 max_size）；
    • 调整 WebSocket 读写缓冲与分片：ws.read_size_hint(4096);、ws.write_buffer_bytes(16384);、ws.auto_fragment(true);；
    • 大量小块数据时考虑 buffers_cat 合并写，减少系统调用。

7.10 未限制 body 大小，被超大请求打爆内存

  • 问题：恶意客户端发一个声明 Content-Length: 100000000000 的请求，服务端 OOM。
  • 原因：parser 默认的 body 上限非常大。
  • 解决：显式设置 parser::body_limit()（以及必要时 header_limit()），超限时解析以 http::error::body_limit 失败。使用高层 http::read 时可通过先 read_header + parser 的方式设置。

7.11 异步服务端忘记重置请求对象

  • 问题：第二个请求解析结果里混入了上一个请求的头部。
  • 原因：http::async_read 会把解析结果写入传入的消息对象，旧字段不会自动清空。
  • 解决：每次读取前执行 req_ = {};（官方 http_server_async.cpp 中即如此）。

7.12 多线程下未使用 strand

  • 问题：偶发数据竞争、回调里状态错乱。
  • 原因：beast::tcp_stream、websocket::stream 都不是线程安全的；io_context 被多线程 run() 时处理器可能并发执行。
  • 解决：为每个连接创建独立的 strand（net::make_strand(ioc)）作为 I/O 对象的 executor；session::run() 里用 net::dispatch(stream_.get_executor(), ...) 保证进入正确上下文。WebSocket 的 stream 尤其要求所有调用在同一 strand 上。

7.13 混淆错误码风格与异常风格

  • 问题：本意用 error_code 处理的错误被抛成异常，或反之异常被吞掉。
  • 原因：Beast 的每个算法几乎都同时提供 error_code& 重载（不抛）与无该参数的重载（抛 beast::system_error）。
  • 解决：全项目统一风格。用 error_code 时注意 beast::error::need_buffer、http::error::end_of_stream、websocket::error::closed 这三个“正常错误”需要特殊处理（清零或当作正常结束）。
