1. 概述

Boost.Asio 是一个跨平台的 C++ 网络与底层 I/O 库，它统一了同步 I/O 与异步 I/O 的编程接口，并额外提供定时器、信号、串口、文件、管道、SSL 等能力。

它解决的问题：

  • 用同一套 API 同时支持**阻塞（同步）和非阻塞（异步）**操作，无需为两种模型写两套代码。
  • 在异步模型下，用少量线程支撑大量并发连接（不需要 thread-per-connection）。
  • 把「发起操作」与「处理结果」解耦，通过 **完成处理器（completion handler）**回调驱动业务逻辑。
  • 屏蔽各平台差异：Linux 上基于 epoll/kqueue 的 Reactor，Windows 上基于 overlapped I/O 与 I/O 完成端口。

典型使用场景：

  1. 高性能 TCP/UDP 服务器与客户端（长连接网关、代理、游戏后端、RPC 框架）。
  2. 需要定时器、超时控制、心跳检测的网络程序。
  3. 需要优雅处理 SIGINT/SIGTERM 并平滑退出的服务进程。
  4. 需要 TLS/SSL 加密传输的客户端与服务器（ssl::stream）。
  5. 把任意计算任务提交到线程池执行（thread_pool + post）。

与标准库/替代方案对比：C++ 标准库目前没有网络库；与裸 socket + select/poll/epoll 相比，Boost.Asio 提供了可移植的异步抽象与对象生命周期管理；与 libevent/libuv 相比，它是 C++ 原生、类型安全且与 STL（std::chrono、std::shared_ptr、std::bind/lambda）深度集成的方案。

3. 核心概念

3.1 I/O 执行上下文（I/O execution context）与 io_context

所有 Asio 程序都至少需要一个 I/O 执行上下文，它代表程序与操作系统 I/O 服务之间的连接。
最常用的是 boost::asio::io_context（也有 boost::asio::thread_pool、boost::asio::system_context）。

3.2 同步操作 vs 异步操作

同步：调用即阻塞，直到操作完成；失败时抛 boost::system::system_error，或者用带 error_code& 参数的重载来避免异常。

异步：调用立即返回，操作完成后由执行上下文调用完成处理器。

3.3 完成处理器（completion handler）与 completion token

异步操作接受一个 completion token，它决定结果如何交付。默认 token 会把「可调用对象」当作 completion handler 直接使用；此外还有 use_awaitable、use_future、detached、as_tuple、redirect_error 等适配器。

3.4 Proactor 模型与线程模型

Asio 的异步基于 Proactor 设计模式：操作系统（或内部 Reactor）完成操作后把事件放入完成事件队列，io_context 取出事件并调用对应的 handler。

关键保证：

  • handler 只会由正在调用 io_context::run()（或 run_one/poll 等）的线程调用。
  • 内部实现线程绝不会直接调用用户代码，并且会阻塞所有信号。
  • 因此线程的创建与管理完全是用户的责任：单线程 run() 即得到「隐式 strand」，
    handler 之间天然不会并发；多线程 run() 则需要显式同步。

3.5 strand：无锁化的线程安全

strand 是一个 executor 适配器，保证通过它分发的 handler 严格串行执行（不会并发），它让你在多线程程序中避免显式加锁，但多个strand之间不保证彼此的handler串行执行。

3.6 buffer：数据的内存视图

I/O 操作传输的是连续内存区域（buffer）。Asio 用 const_buffer / mutable_buffer 表示单个缓冲区，用 MutableBufferSequence / ConstBufferSequence 概念表示缓冲区序列，从而实现 scatter-gather。

生命周期铁律：异步操作进行期间，buffer 指向的内存必须保持有效，直到 handler 被调用。

3.7 流式 I/O、短读短写与 read/write

流式对象（TCP socket、SSL stream 等）没有消息边界，read_some()/write_some() 可能只传输一部分数据（short read / short write）。若需要「读满 N 字节」或「写完全部数据」，应使用组合操作：

boost::asio::thread_pool 是一个自带线程的执行上下文，可用 post() 提交计算任务，用 join() 等待全部完成。

3.9 C++20 协程

co_spawn + awaitable<T> + use_awaitable 让异步逻辑写成同步风格，co_await 表达式在出错时抛出 boost::system::system_error。

5. 使用流程

5.1 同步 TCP 客户端流程

  1. 创建 boost::asio::io_context io_context;（同步操作也需要它来访问 I/O 服务）。
  2. 构造 tcp::resolver resolver(io_context);，调用 resolver.resolve(host, service)
    得到 results_type endpoints（可能含多个 IPv4/IPv6 端点）。
  3. 构造 tcp::socket socket(io_context);，调用 boost::asio::connect(socket, endpoints)
    依次尝试各端点，直到连接成功（失败时抛 system_error）。
  4. 发送数据：boost::asio::write(socket, boost::asio::buffer(request, n));
    —— 用组合写保证「写全」；或带 error_code 版本避免异常。
  5. 接收数据：boost::asio::read(socket, boost::asio::buffer(reply, n));
    —— 读满期望字节数。若长度未知，可循环 socket.read_some()，
    并用 if (ec == boost::asio::error::eof) break; 判断对端正常关闭。
  6. 错误处理：要么整体 try { ... } catch (std::exception& e) { std::cerr << e.what(); }，
    要么对每个调用使用 error_code 重载并逐个检查。
  7. 关闭顺序：数据收发完毕后，若需通知对端「我不再发送」，先
    socket.shutdown(tcp::socket::shutdown_send);，读尽对端剩余数据后再 socket.close();。
    socket 析构会自动 close()，但显式关闭更清晰、更早释放资源。
  8. io_context 在同步模式下无需 run()；作用域结束时正常析构即可。

5.2 同步 TCP 服务端流程

  1. 创建 io_context。
  2. 构造 tcp::acceptor acceptor(io_context, tcp::endpoint(tcp::v4(), port));
    （便捷构造会依次完成 open + bind + listen，并默认开启 reuse_address）。
    若需更细控制：acceptor.open(protocol); acceptor.set_option(tcp::acceptor::reuse_address(true)); acceptor.bind(endpoint); acceptor.listen();
  3. 进入循环：为每个连接创建一个 tcp::socket socket(io_context);。
  4. acceptor.accept(socket); 阻塞直到有新连接到达。
  5. 处理该连接：读取请求 → 构造响应 → boost::asio::write(socket, ...)。
  6. 错误处理：整个服务逻辑包在 try/catch (std::exception&) 中；
    单个连接的异常应就地捕获，避免整个服务退出。
  7. 连接处理完后 socket 析构自动关闭；若要并发处理多个客户端，
    把 session(socket) 交给 std::thread(...).detach() 或改用异步服务端。
  8. 关闭顺序：先 acceptor.close();（停止接受新连接），
    再等待/结束已建立的连接，最后让 io_context 析构。

5.3 异步 TCP 服务端流程

  1. 创建 io_context，用 tcp::acceptor 绑定并监听端口（同 5.2 步骤 2）。
  2. 定义「接受循环」do_accept()：调用 acceptor_.async_accept(...)，
    在 handler 中先 if (!ec) { 创建 session 并 start(); }，然后立即再次调用 do_accept()
    以接受下一个连接。
  3. 每个连接由 session 对象管理，session 继承
    std::enable_shared_from_this<session>，用 std::make_shared<session>(std::move(socket)) 创建。
  4. 在 session 的每次异步调用中捕获 auto self = shared_from_this();
    并放进 lambda，保证 session 在 handler 执行期间存活。
  5. 读循环 do_read()：socket_.async_read_some(buffer(data_, max_length), ...)，
    handler 中若 !ec 则调用 do_write(length)。
  6. 写循环 do_write()：boost::asio::async_write(socket_, buffer(data_, length), ...)，
    handler 中若 !ec 则回到 do_read()，形成「读-写-读」状态机。
  7. 错误处理：handler 中检查 ec；正常关闭会产生 error::eof，
    取消操作会产生 error::operation_aborted，两者通常只需结束该 session，
    不必上报为致命错误。
  8. 最后调用 io_context.run();（可多线程调用以形成线程池）。
  9. 关闭顺序：收到退出信号时（配合 signal_set）先 acceptor_.close()，
    再 close()/stop_all() 所有 session 的 socket 以取消未完成操作；
    当所有 handler 返回且无未完成工作后，run() 自然返回。

5.4 SSL/TLS 客户端流程

SSL 客户端 = 「TCP 客户端流程（5.1）」+「上下文准备 + 主机校验 + 握手」，顺序如下：

  1. 创建上下文：ssl::context ctx(ssl::context::tls_client);（客户端用 tls_client，服务端用 tls_server）。
  2. 配置如何校验对端：ctx.set_default_verify_paths();（用系统 CA 库）
    或 ctx.load_verify_file("ca.pem"); / ctx.add_verify_path("certs/");；
    需要更严格时再设 ctx.set_verify_depth(n);。
  3. 解析目标：tcp::resolver resolver(io); auto endpoints = resolver.resolve(host, port);
    （HTTPS 的端口通常是 443，服务名可直接写 "https"）。
  4. 构造加密流：ssl::stream<tcp::socket> stream(io, ctx);
    —— 注意它不自带连接能力，连接要作用在底层套接字上。
  5. 连接底层 TCP：boost::asio::connect(stream.lowest_layer(), endpoints);
    （异步版本用 async_connect(stream.lowest_layer(), endpoints, ...)）。
    可选：stream.lowest_layer().set_option(tcp::no_delay(true));
  6. 打开 SNI：SSL_set_tlsext_host_name(stream.native_handle(), host.c_str());
    —— 把主机名发给对端。CDN、云负载均衡、虚拟主机依赖它选择正确证书；缺了它常表现为握手失败或拿到默认证书。
  7. 设置校验策略（两步，缺一不可）：
    1. stream.set_verify_mode(ssl::verify_peer); —— 校验证书链；
    2. stream.set_verify_callback(ssl::host_name_verification(host)); —— 校验证书主机名。
  8. 握手：stream.handshake(ssl::stream_base::client);
    （异步版本 stream.async_handshake(ssl::stream_base::client, ...)）。
    握手期间会调用第 7 步的回调；失败抛 system_error（用 error_code 重载则返回错误）。
  9. 收发数据：握手完成后把 stream 当普通流用 —— boost::asio::write() / read()、
    async_write() / async_read()；若协议里有行分隔符，用 streambuf + async_read_until()。
  10. 优雅关闭：数据交换结束后调用 stream.shutdown()（或 async_shutdown()）发送 TLS
    close_notify；async_shutdown 可能返回 error::eof（对端已先关闭），一般可忽略。
    随后关闭底层连接：stream.lowest_layer().close();。
  11. 双向认证（mTLS，可选）：在 ctx 上 use_certificate_chain_file(...) +
    use_private_key_file(...) 提供客户端证书。
  12. 多线程：所有异步 SSL 操作必须在同一个 strand 上执行（ssl::stream 自身不加锁）。

5.5 SSL/TLS 服务端流程

SSL 服务端 = 「异步 TCP 服务端流程（5.3）」+「证书配置 + 逐个连接握手」：

  1. 创建上下文：ssl::context ctx(ssl::context::tls_server);
  2. 配置证书与私钥：ctx.use_certificate_chain_file("server.pem");
    ctx.use_private_key_file("server.pem", ssl::context::pem);
    —— 私钥若有口令，先 ctx.set_password_callback(...)。
  3. 可选加固：ctx.set_options(default_workarounds | no_sslv2 | no_sslv3 | single_dh_use);
    使用 DHE 套件时还要 ctx.use_tmp_dh_file("dh4096.pem");
  4. 监听 TCP：tcp::acceptor acceptor(io, tcp::endpoint(tcp::v4(), port));（同 5.2 步骤 2）。
  5. 接受连接：acceptor.async_accept(...) 拿到的是未加密的 tcp::socket；
    用它和 ctx 构造加密流 —— ssl::stream<tcp::socket>(std::move(socket), ctx)，
    然后交给 session 对象（enable_shared_from_this）并 start()。
  6. 先握手再读写：session 的第一步是
    socket_.async_handshake(ssl::stream_base::server, ...);
    只有握手成功（!ec）才进入读写循环。
  7. 读写循环：与 TCP 服务端相同的「读-写-读」状态机，只是操作对象换成 ssl::stream
    （async_read_some() / async_write()）。
  8. 要求客户端证书（mTLS，可选）：
    ctx.set_verify_mode(ssl::verify_peer | ssl::verify_fail_if_no_peer_cert);
  9. 关闭：数据结束后 async_shutdown() 发送 close_notify；
    关闭 acceptor 停止接受新连接（同 5.2 步骤 8）。
  10. 多线程：每个连接的异步操作同样要串行化到同一个 strand 上。

7. 常见问题与陷阱

  1. 问题：io_context.run() 立刻返回，程序什么都没做就结束了。
    原因：调用 run() 时没有任何未完成的异步操作，io_context 无「工作」可做。
    解决：确保在 run() 之前已经发起了至少一个异步操作（如 async_wait/async_accept）；
    若必须先启动 run() 线程再添加工作，用 auto work = boost::asio::make_work_guard(io); 守住。

  2. 问题：run() 一直不返回，程序退不出来。
    原因：仍有未完成操作或存在 work guard；或 acceptor 一直在等待新连接。
    解决：收到退出条件时调用 io.stop()（放弃剩余工作），
    或先 acceptor.close() + 关闭所有 socket 取消未完成操作，
    再 work.reset() 让 run() 自然结束。用 stop() 后若要再次运行，必须先 io.restart()。

  3. 问题：异步操作回调时崩溃（野指针/已析构对象）。
    原因：对象生命周期短于异步操作。典型写法：
    void f(){ std::string msg = "hi"; async_write(sock, buffer(msg), h); } —— msg 在函数返回即析构。
    解决：让被引用对象活到 handler 完成：使用 std::enable_shared_from_this +
    auto self = shared_from_this(); 并在 lambda 中按值捕获 self；
    或把数据放进成员变量 / std::shared_ptr<std::string> 并在 handler 中按值捕获。

  4. 问题：handler 执行很慢时整个服务「卡住」。
    原因：handler 在 run() 线程中执行，阻塞式操作（sleep、同步 DNS、同步文件 I/O、
    长时间计算、同步 read/write）会阻塞事件循环，导致其它连接得不到处理。
    解决：handler 必须尽快返回。耗时工作交给 boost::asio::thread_pool 或
    独立线程池执行，完成后用 boost::asio::post(io, ...) 把结果投回事件循环。

  5. 问题：多线程下 io_context.run() 导致数据竞争（如共享的 count_、std::cout）。
    原因：多个线程调用 run() 时，handler 可能真正并发执行。
    解决：用 strand：auto strand = boost::asio::make_strand(io);，
    把 handler 通过 boost::asio::bind_executor(strand, handler) 绑定；
    或直接在创建 I/O 对象时使用 strand executor。仅使用单线程 run() 时是隐式 strand，无需加锁。

  6. 问题：同一个 socket 上同时发起两个异步读（或两个异步写），行为异常。
    原因：流式 socket 上同一时刻只允许一个未完成的异步读和一个未完成的异步写。
    解决：用「一次读/写完成后在 handler 中再发起下一次」的状态机模式（见示例 5 的
    do_read/do_write）；需要并发读写不同数据时，用队列串行化写操作。

  7. 问题：async_read_some 只读到一部分数据就返回了。
    原因：这是「短读」，流式 I/O 的正常行为，read_some 不保证读满。
    解决：需要读满固定字节数时使用组合操作 boost::asio::async_read(sock, buffer(data, n), h)
    或 boost::asio::read(sock, buffer(data, n))；需要按行读取时使用
    async_read_until(sock, sb, "\r\n", h)。

  8. 问题：async_read_until 之后的数据「丢了」。
    原因：read_until 返回的字节数包含分隔符，分隔符之后可能还有已读入的多余数据。
    解决：多余数据仍留在 streambuf 中，不要清空它；用 streambuf 的
    data()/consume(n) 精确消费已处理的部分，把剩余数据留给下一次读取。

  9. 问题：定时器 handler 被调用时 ec == boost::asio::error::operation_aborted。
    原因：expires_after()/expires_at() 会取消正在进行的等待，或调用了 cancel()。
    解决：这是预期行为。检查 expires_after() 的返回值（被取消的等待数）来判断
    「设置新超时」是否成功；在 handler 中显式忽略 operation_aborted。

  10. 问题：服务端重启时报 Address already in use。
    原因：端口处于 TIME_WAIT 状态且未开启地址复用。
    解决：acceptor.set_option(boost::asio::ip::tcp::acceptor::reuse_address(true));
    （用便捷构造 tcp::acceptor a(io, endpoint) 时默认已开启）。

  11. 问题：boost::asio::buffer(msg) 在异步操作期间悬空，程序随机崩溃或断言失败。
    原因：buffer() 只创建视图，不复制数据；底层内存必须存活到 handler 调用。
    解决：把数据放进 shared_ptr 或成员变量；开启缓冲区调试
    （MSVC 默认，GCC 定义 _GLIBCXX_DEBUG）可让越界/失效在调试版中触发断言。

  12. 问题：thread_pool 析构时程序 std::terminate。
    原因：thread_pool 析构要求所有任务已完成，未调用 join()（或 stop()）。
    解决：作用域结束前显式调用 pool.join();（等待完成）或 pool.stop();（放弃剩余任务）。

  13. 问题：协程里 co_await 直接抛异常，导致协程终止。
    原因：默认 use_awaitable 会把 error_code 转成 system_error 异常；
    co_spawn 的 handler 收到 std::exception_ptr，若用 detached 则异常被忽略。
    解决：在协程内部 try/catch；或使用 as_tuple / redirect_error
    显式接收 error_code（见官方 overview/composition/cpp20_coroutines.html）。

  14. 问题：boost::asio::ip::tcp::resolver::resolve 阻塞很久。
    原因：resolve 是同步调用，可能触发阻塞式 DNS 查询。
    解决：在服务器/高并发场景使用 async_resolve()；或把同步解析放到独立线程执行。

  15. 问题：SSL 流上的异步操作在多线程下数据错乱。
    原因：ssl::stream 自身不做任何加锁。
    解决：所有 SSL 异步操作必须在隐式或显式 strand 上执行
    （见官方 overview/ssl.html 的 “SSL and Threads”）。

  16. 问题：客户端设了 verify_peer 仍被中间人攻击。
    原因：verify_peer 只校验证书链是否可信，不校验证书主机名；任意可信 CA 签发的
    任意域名证书都能通过。
    解决：必须同时 stream.set_verify_callback(ssl::host_name_verification(host));
    （见 §5.4 步骤 7、§4.2 host_name_verification）。

  17. 问题：连接某些 HTTPS 站点握手失败，或拿到与域名不符的默认证书。
    原因：没有发送 SNI。
    解决：连接成功后、握手前调用
    SSL_set_tlsext_host_name(stream.native_handle(), host.c_str());
    —— 虚拟主机 / CDN / 负载均衡必须依赖 SNI 才能返回正确证书。

  18. 问题：对端日志出现 stream truncated（TLS 流被截断）。
    原因：我方关闭连接时只 close() 了 TCP，没有发送 TLS close_notify。
    解决：数据收发结束后先 stream.shutdown()（或 async_shutdown()）；
    async_shutdown 返回 boost::asio::error::eof 属正常情况（对端先关闭）。

  19. 问题：直接对 ssl::stream 调用 connect()，编译报错或行为异常。
    原因：ssl::stream 不是套接字，没有 connect()。
    解决：连接 / 接受一律作用在底层套接字上 ——
    boost::asio::connect(stream.lowest_layer(), endpoints);。
