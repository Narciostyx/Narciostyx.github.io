TCP协议

TCP协议字段、状态转移与拥塞控制

  • TCP协议的连接是一对一，因此基于广播和多播的应用程序不能使用TCP服务，更适合使用UDP服务
  • TCP模块发送的TCP报文段的个数和应用程序执行的写操作次数之间没有固定数量关系
  • 接收端收取TCP接收缓冲区的数据时，可以一次性全部读出，也可以分多次读取，取决于当前用户指定的应用程序缓冲区大小
    • UDP则不同，发送端每次执行一次写操作，UDP模块就封装发送，接收端必须即使针对每个UDP数据报进行读操作，否则就会丢包
    • 若用户没有指定足够大小的缓冲区读取UDP数据，则UDP数据将被截断

  • 32位确认号，即将收到的TCP报文段的序号值加1用作响应，如：
  • 6位标志位，如下：
    • URG，表示紧急指针是否有效
    • ACK，表示确认号是否有效（确认报文段）
    • PSH，表示接收端应用程序应立即从TCP接收缓冲区内读走数据，为后续数据腾出空间
    • RST，表示要求对方重新建立连接（复位报文段）
    • SYN，表示建立一个请求（同步报文段）
    • FIN，表示本段将关闭连接（结束报文段）
  • 16位窗口大小，TCP流量控制的手段，这里的窗口指接收通告窗口RWND（Receiver Window），告诉对方本端TCP接收缓冲区还能容纳多少字节数据，便于对方控制数据发送速度
  • TCP校验和不仅包含头部，还包含数据部分，这是TCP可靠传输的一个重要保障
  • 紧急指针，与序号字段的值相加表示最后一个紧急数据的下一字节序号（相当于偏移量，相对于当前序号的偏移量）
  • 头部选项，最大40字节，其结构一般为：
    • 第一个字段代表选项类型
    • 第二个代表该选项的总长度，包含kind与length占据的两字节
    • 第三个代表具体信息

    • 选项表结束选项
    • 空操作，通常为了将TCP选项的总长度填充为4字节的整倍数
    • 最大报文段长度选项，TCP连接初始化时，使用该选项协商最大报文长度MSS，通常其值为（MTU-最短IP头部20字节-最短TCP头部20字节），因此对于以太网来讲，通常为1460字节
    • 窗口扩大因子选项，TCP连接初始化时，使用该选项协商RWND的扩大因子，在TCP头部中，RWND的最大值为65535字节（2的16次方减一），但实际TCP模块允许的RWND大小远不止这个数，因此该选项解决了这个问题
      • 假设当前RWND大小为N，窗口扩大因子为M，则实际RWND大小为N乘以2的M次方（M取值范围为0~14）
      • 可通过修改/proc/sys/net/ipv4/tcp_window_scaling启动或关闭该选项
      • 与MSS选项用于，因为这两个选项仅用于TCP连接初始化，因此只能出现在同步报文中，否则被忽略
    • SACK，即选择性确认选项
      • TCP通信时，若某个TCP报文段丢失，则TCP模块会重发最后被确认的TCP报文后的所有报文，导致部分正确传输报文也被重复发送，降低TCP性能
      • SACK改善该问题，只重发丢失的TCP报文段，而非重发所有后续未确认的报文
      • 修改/proc/sys/net/ipv4/tcp_sack启动或关闭该选项
    • SACK实际工作的选项，告诉发送方本端已收到并缓存的不连续数据块，从而让发送方检查并重发丢失的数据块
      • 每个块边沿包含一个四字节的序号，其中左边沿表示不连续块的第一个数据序号，而右边沿表示不连续块的最后一个数据序号的下一个序号
      • 这样一对参数之间的数据是没有收到的，因为一个块信息占据8字节，最多可包含4个这样的不联系块
    • 时间戳选项，计算双方的RTT（Round Trip Time，即回路时间），为流量控制提供信息

  • iptables命令
    • 与firewalld命令都是用于管理防火墙，定义其各种功能规则
      • iptables基于接口设置规则，firewalld基于区域设置规则（与硬件防火墙设置类似）
      • 前者配置在/etc/sysconfig/iptables，后者一般在/etc/firewalld与/usr/firewalld中
      • 前者为静态防火墙，后者为动态防火墙，且可以在运行时改动
      • firewall-cmd进行配置，分为9个区域：trusted（允许所有流量）、public、external、home、internal、work、dmz、block（拒绝所有传入流量）与drop（丢弃所有传入流量，不产生ICMP错误响应）
      • 区域的安全程度取决于管理员设置的规则，默认情况下，均为public区域
    • 该命令有Filter（基本数据包过滤）、NAT（处理NAT）、Mangle（改变数据包）、Raw（在连接跟踪前配置数据包）四种规则处理类别，其中Filter表为其默认表（tables）
    • 有INPUT OUTPUT FORWARD三种处理数据包的规则（chains）
    • 规则包含一个条件及目标，满足条件就执行目标中的规则，否则执行下一条规则
    • 下介绍部分选项：
      • --list或-L，列举规则，如iptables -t filter -L列举filter表中的规则
      • -t name，name为具体规则处理类型（表）
      • --append或-A chain，追加当前规则到chain链，如iptables -A INPUT -p tcp -dport 80 -j ACCEPT，增加到INPUT链，允许目标端口为80的TCP连接到本机
      • --jump或-j target，执行对应行为，如ACCEPT或DROP行为，iptables -A INPUT -s 192.168.1.100 -j DROP，拒绝来自192.168.1.100的任何连接
  • TCP连接的重连操作次数由/proc/sys/net/ipv4/tcp_syn_retries定义，当达到目标重连次数，TCP放弃连接并通知应用程序

TCP状态转移

  • 图中粗虚线代表典型的服务器端连接的状态转移，粗实线代表客户端（CLOSED代表假想的起始点，并非一个实际状态）
  • 使用netstat命令可以查看当前TCP连接的状态
  • 服务器端
    1. 调用listen进入LISTEN监听状态，即被动打开
    2. 监听到某个连接请求，将该连接放入内核等待队列中，并发送带SYN的确认报文，进入SYN_RCVD状态
    3. 若服务器接受到客户端发送回的确认报文段，进入ESTABLISHED状态
    4. 当客户端主动发送关闭连接时，服务器返回确认报文段并进入CLOSE_WAIT状态，即等待服务器端应用程序关闭连接，随后进入LAST_ACK状态
    5. 接受到客户端的确认报文段后进入CLOSED状态
  • 客户端
    • 调用connect发送同步报文段，进入SYN_SENT状态
      • 若服务器目标端口不存在，或被TIME_WAIT状态的连接占用，则服务器返回RST，调用失败
      • 若服务器端口存在但超时，调用失败
      • 调用失败返回CLOSED状态
    • 客户端主动发送结束报文段，进入FIN_WAIT_1状态，若收到服务器发送的确认报文段则进入FIN_WAIT_2状态，此时服务器处于CLOSE_WAIT状态，若此时服务器也发送结束报文段，则客户端确认并进入TIME_WAIT状态
  • 处于FIN_WAIT_2状态的客户端需要等待服务器发送结束报文段，否则将一直停留在该状态，此时若客户端强序退出，该连接将被内核接管，变成孤儿连接
    • /proc/sys/net/ipv4/tcp_max_orphans与/proc/sys/net/ipv4/tcp_fin_timeout定义了内核接管的孤儿连接数目以及生存时间
  • 当客户端处于TIME_WAIT状态时，客户端需要等待一段长为2MSL（Maximum Segment Life，报文段最大生存时间）的时间，才会关闭，MSL在RFC文档中建议值为2min，设置TIME_WAIT状态的原因如下：
    • 保证TCP连接被可靠地终止（如：在TIME_WAIT状态发送给服务器的确认报文丢失，服务器会重发结束报文段，因此客户端需要停留在某个状态以处理重复收到的结束报文段）
    • 保证让迟来的TCP报文段有足够时间被识别丢弃
    • Linux系统上，一个TCP端口不能被同时打开多次，在TIME_WAIT状态下，无法立即使用该占用端口
    • 因为TCP报文段的最大生存时间是MSL，因此坚持2MSL时间的TIME_WAIT状态可以确保网络上两个传输方向上尚未接收到、迟到的TCP报文段都被丢弃

RST报文段

  • 当下列三种情况时，会发送RST报文段，通知对方关闭连接或重新建立连接
    1. 访问不存在的端口
    2. 异常终止连接（一旦发送了复位报文段，发送端的所有排队等待发送的数据都将被丢弃）
    3. 处理半打开连接（当某端关闭或异常终止了连接，而对方没有收到结束报文，此时这端仍维持着原本的连接，某端即使重启也不会有原来连接的任何信息，此时成为半打开状态，此时往该连接写入数据，对方将回应复位报文段）

TCP连接交换的应用程序数据

  • TCP报文段携带的应用程序数据按照长度分为两种：
    1. 交互数据，仅包含很少的字节，使用该数据的应用程序对实时性要求高
    2. 成块数据，使用数据的应用程序对传输效率要求高
  • nagle算法（解决交互数据在广域网上数量庞大可能导致拥塞发生的问题）：一个TCP连接的通信双方在任意时刻都最多只能发送一个未被确定的TCP报文段，在该TCP报文段的确认到达之前不能发送其他TCP报文段（发送方可以在等待确认的同时收集本端需要发送的微量数据（交互数据），在收到确认报文段后全部发出），其具备自适应性，确认到达得越快，数据就发送的越快
  • tcpdump命令，是Linux上的网络抓包工具，下为常见选项以及过滤表达式：
    • -i dev，监听指定网卡dev
    • -n，不解析域名
    • -nn，不解析域名且不解析端口服务号
    • -c n，抓取n个包后自动退出
    • -s n，抓取n字节数据包，为0代表不截断，默认68字节
    • -I，抓包保存到文件同时查看包的内容
    • -v/-vv
    • -w file，写入文件file中（便于如wireshark分析）
    • -r file，读取pcap文件
    • -A，以ASCII码显示数据包内容
    • -X，以16进制与ASCII同时显示
    • 类型过滤：host 192.168.1.1、net 192.168.22.0/24、port 22
    • 方向过滤：src 10.0.0.1、dst port 80
    • 协议过滤：tcp udp icmp arp
    • 逻辑组合：and or not
    • 支持高级协议字段过滤，语法如下：
      1. proto[x:y]，过滤从x字节开始的y字节数
      2. proto[x:y] & z=0，proto[x:y]和z的操作不为0
      3. e.g.tcp[tcpflags] & tcp-syn !=0，即tcp包的标志位为SYN

带外数据

  • O（ut）O（f）B（and），用于迅速通告对方本端发生的重要事件，因此其具有比普通数据更高的优先级，应该总是被立即发送，且不论缓冲区是否有排队等待发送的普通数据
  • UDP没有实现带外数据，TCP也没有真正的带外数据，但可以利用其头部的紧急指针标志与紧急指针两个字段
  • TCP发送紧急数据（带外数据）的过程：
    • 假定该进程已经往某个TCP连接的发送缓冲区写入N个字节的普通数据，并等待发送
    • 在发送前写入三个字节的带外数据abc，此时TCP报文段的头部将设置URG标志，并设置紧急指针为指向最后应该带外数据的下一字节，如下图：
    • 由图可知，只有最后一个字节被当作带外数据（字母c），其余为普通数据，并将其读入一个特殊的缓存中，这个缓存只有1个字节，成为带外缓存，若为即使取走，则会被覆盖（如果后续有其他带外数据）

TCP超时重传

  • TCP服务必须能够重传超时时间内未收到确认的TCP报文段，因此需要为每个报文段都维护一个重传定时器，定时器在报文段第一次被发出时启动，若超时，重传时间、重传次数由TCP的重传策略决定
  • iperf是一个测量网络状况的工具，-s代表以服务器启动，默认监听端口5001，并丢弃当前监听端口收到的所有数据
  • /proc/sys/net/ipv4/tcp_retries1/2，前者指定TCP最少执行的重传次数，默认为3，后者为最多可执行的重传次数，默认为15

拥塞控制

  • 提高网络利用率、降低丢包率，并保证网络资源对每条数据流的公平性也是TCP模块的主要任务，也就是拥塞控制
  • 拥塞控制拥有四个部分：
    • 慢启动（slow start）
    • 拥塞避免（congestion avoidance）
    • 快速重传（fast restransmit）
    • 快速恢复（fast recovery）
    • /proc/sys/net/ipv4/tcp_congestion_control文件指示当前机器使用的拥塞控制算法，如cubic算法、reno算法、vegas算法等
    • 拥塞控制的最终受控变量是发送端向网络一次连续写入（收到第一个数据确认之前）的数据量，即SWND（Send Window），同时S（ender）MSS一般等于MSS
    • 发送端需要合理选择SWND大小，如果太小则会引起网络延迟，太大会导致网络拥塞，接收方可以通过RWND去控制SWND，但显然不够，因此发送端引入了拥塞窗口C（ongestion）WND的状态变量，实际的SWND值是RWND与CWND中的较小值

慢启动与拥塞避免

  • TCP连接建立后，CWND将会被设置为初始值I（nitial）W（indow），大小为2~4个SMSS（新Linux内核提高了该初始值），此后发送端每收到接收端的一个确认，其CWND就按照CWND+=min(N,SMSS)的方式增加，其中N为此次确认中包含的之前未被确认的字节数（即之前没被确认，接收端刚确认收到的字节数），因此CWND每轮会增加最多不超过一个SMSS的大小
  • 慢启动算法的理由：TCP模块刚开始发送数据，不清楚网络当前的实际情况，需要用一种试探性的方式平滑增长CWND的大小（实际慢启动增长速度极快），当然，若不施加其他手段，慢启动将导致CWND很快膨胀，因此TCP拥塞控制定义了另外一个状态变量：慢启动门限（ssthresh，即slow start threshold size），当CWND大小超过该值时，进入拥塞避免阶段
  • 慢启动增长速度快的原因
  • 拥塞避免算法使得CWND按照线性方式增加，减缓其扩大，在RFC文档中提到下列两种方式：
    1. 每个RTT时间内按照CWND+=min(N,SMSS)计算新的CWND，而不论该RTT时间发送端收到了多少个确认（这里N代表该RTT内累计确认的新字节数，而非单个收到确认报文段）
    2. （Linux下的主流实现）每收到一个对新数据的确认，按照CWND+=SMSS*SMSS/CWND来更新CWND
    • 不论哪种算法，均为让CWND每个RTT只增加1个SMSS，如下图：
  • 发送端判断拥塞发生的依据：
    • 传输超时，或TCP重传定时器溢出（慢启动与拥塞避免）
    • 接收到重复的确认报文段（快速重传与快速恢复）
    • 若为第一种情况，即发送端检测到拥塞发生是由于传输超时，将做如下调整：ssthresh=max(FlightSize/2,2*SMSS) CWND<=SMSS（FlightSize为已发送但未收到确认的字节数），这样调整后，CWND将小于SMSS，也必然小于新的ssthresh，故而拥塞控制再次进入慢启动阶段

快速重传和快速恢复

  • 很多情况下，发送端都可以收到重复的确认报文段，比如TCP报文段丢失，接收端收到乱序报文段并重排等，拥塞控制算法需要判断当前网络是否真的发生了拥塞（TCP报文段是否真的丢失）：发送端若连续收到3个确认报文段，就认为拥塞发生，将启动快速重传与快速恢复算法：
    1. 当收到第3个重复的确认报文段时，按照ssthresh=max(FlightSize/2,2*SMSS) CWND<=SMSS计算ssthresh，然后立即重传丢失报文段。并按照CWND=ssthresh+3*SMSS设置CWND
    2. 每次收到一个重复的确认时，设置CWND=CWND+SMSS，此时发送端可以发送新的TCP报文段
    3. 收到新数据的确认时，设置CWND=ssthresh，快速重传和快速恢复完成之后，拥塞控制将恢复到拥塞避免阶段
